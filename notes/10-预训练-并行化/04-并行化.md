## 〇、本节回答什么

> 训练 70B+ 模型，单 GPU 显存（80-141 GB）远远不够。如何把模型 / 数据 / 计算切到几百甚至上万张 GPU 上？

七种并行维度，**正交可组合**：

| 维度 | 切什么 | 单位 | 通信原语 | 通信粒度 |
|------|--------|------|---------|---------|
| DP (Data Parallel) | batch | 不同 GPU 不同样本 | AllReduce | step 末 |
| ZeRO / FSDP | optim state + param | DP 的精细化 | AllGather + ReduceScatter | layer 内 |
| TP (Tensor Parallel) | 矩阵 | 横/竖切权重 | AllReduce | layer 内 |
| SP (Sequence Parallel) | activation 沿 seq | TP 的扩展 | AllGather + ReduceScatter | layer 内 |
| PP (Pipeline Parallel) | 层 | layer 分组 | Send/Recv | stage 边界 |
| EP (Expert Parallel) | expert | MoE 专属（§9.4） | All-to-All | MoE layer 内 |
| CP (Context Parallel) | seq | 长 context 专用 | P2P ring | attention 内 |

实操：**5D-7D 并行嵌套**（DeepSeek-V3 用了 5D：DP+PP+EP+SP+ZeRO1；Llama-3.1 用了 5D：DP+TP+PP+CP+FSDP）。

本节核心要回答：
1. **每种并行的通信代价精确公式是什么？** 决定选型边界
2. **哪些并行可以叠加、哪些互斥？** 决定 5D 组合的可行域
3. **训练 1k 卡集群时怎么把 5D rank 映射到 NVLink / IB / 跨机架的物理拓扑？** —— 工业实战核心
4. **DualPipe / Zero-Bubble PP / Interleaved 1F1B 三种 PP 调度的具体 timeline 长什么样？** 大厂面试必考

## 一、Data Parallel (DP)

### 1.1 经典 DDP

```
GPU0:  weight_full + batch_chunk_0  ──→ forward → backward → grad_0 ─┐
GPU1:  weight_full + batch_chunk_1  ──→ forward → backward → grad_1 ─┼─→ AllReduce → 同步 grad
GPU2:  weight_full + batch_chunk_2  ──→ forward → backward → grad_2 ─┤    ↓
GPU3:  weight_full + batch_chunk_3  ──→ forward → backward → grad_3 ─┘ optimizer.step()
```

每 step 1 次 AllReduce 全部 gradient。**通信量 = $2(N-1)/N \cdot |W|$**（ring all-reduce）。

显存：每卡都有完整 weight + grad + optimizer state → 大模型存不下。

→ 故而引入 ZeRO / FSDP。

### 1.2 DDP 通信 overlap

PyTorch DDP 的标准优化：**Reverse-order bucket all-reduce**。

```
backward 计算 layer L → layer 1
                ↓
        每攒够一个 bucket（25MB 默认）→ 异步 AllReduce
        计算继续往前传，AllReduce 在后台跑
        backward 结束时，AllReduce 也基本完成
```

→ DDP 的通信几乎完全被计算 hide 掉。这是 DDP 在中小模型上仍最快的原因。

## 二、ZeRO（DeepSpeed）/ FSDP（PyTorch）

[ZeRO: Memory Optimizations Toward Training Trillion Parameter Models (Rajbhandari 2019)](https://arxiv.org/abs/1910.02054)

把"全部冗余存在每卡"的 DP 模式拆分：

| Stage | 切分什么 | 每卡显存 (per param) | 通信增量 vs DDP |
|-------|---------|---------------------|---------|
| Baseline DDP | 都不切 | 16 B | AllReduce(grad) |
| **ZeRO-1** | optimizer state 分片 | 4+12/N B | 同 DDP |
| **ZeRO-2** | + grad 分片 | 4+(12+4)/N B | ReduceScatter 取代 AllReduce |
| **ZeRO-3 = FSDP** | + param 分片 | (4+12+4)/N B = 16/N | AllGather(param) ×2 + ReduceScatter(grad) |

（per param 算法：bf16 weight 2B + bf16 grad 2B + fp32 master 4B + fp32 m 4B + fp32 v 4B = 16B）

### 2.1 ZeRO-3 / FSDP 关键流程

```
forward 一个 layer:
  1. AllGather(param_shard) → 凑齐 full weight
  2. compute forward
  3. 释放 full weight，只留 shard

backward 一个 layer:
  1. AllGather(param_shard) → 凑齐 full weight
  2. compute backward
  3. ReduceScatter(grad) → 每卡只保留自己 shard 对应的 grad

update:
  4. local optimizer step on (param_shard, m_shard, v_shard, grad_shard)
```

通信代价：**每个 layer 2 次 AllGather + 1 次 ReduceScatter**。

总通信量 ≈ DDP × 1.5（一次 AllReduce = 1 次 ReduceScatter + 1 次 AllGather；FSDP 多了 1 次 AllGather）。

但显存几乎 = `total / N`，N=64 时单卡只需 1/64 的 state。

### 2.2 FSDP 的 forward / backward prefetch

如果朴素实现，每个 layer 的 AllGather 都阻塞计算 → GPU idle。

PyTorch FSDP 优化：

```
forward layer L:    [compute L]
forward layer L+1:                   [compute L+1]
                                              ↑
                       AllGather L+1 [发起] -─┘  ← 在 L 计算时就 prefetch L+1 的 param
```

backward 同理：reverse direction prefetch。

实测：prefetch 后 FSDP 计算利用率 ≈ DDP（差距 < 5%）。

### 2.3 ZeRO++ — 进一步通信优化

[ZeRO++ (Wang 2023)](https://arxiv.org/abs/2306.10209)：

1. **qwZ (Quantized Weight comm)**：AllGather param 时压缩到 INT8/FP8 → 通信量减半
2. **hpZ (Hierarchical Param Partition)**：节点内 replicate param（NVLink 快），节点间 partition；forward AllGather 只在节点内 → 砍掉跨节点流量
3. **qgZ (Quantized Gradient comm)**：ReduceScatter grad 时 INT4 量化 + 误差补偿

→ ZeRO++ 在 1024 卡 + 跨机 IB 环境下，相对 ZeRO-3 **吞吐 ↑ 2×**（通信瓶颈缓解）。

### 2.4 HSDP（Hybrid Sharded Data Parallel）

PyTorch FSDP 2024 新增模式：

```
HSDP = "节点内 FSDP，节点间 DDP"

8 节点 × 8 GPU = 64 卡:
  节点内 8 卡: FSDP (param 切 8 份)
  节点间 8 节点: DDP (各节点持有同一份切片，AllReduce 同步 grad)
```

好处：
- 节点内 NVLink 走 FSDP（AllGather 便宜）
- 节点间 IB 走 DDP（每 step 1 次 AllReduce，频次低）
- **显存 = 1/8 而非 1/64**（节点内切，节点间复制）

权衡：用 8× 显存冗余换跨节点通信减少 → 大集群跨机带宽紧时是赢的。

### 2.5 ZeRO-Offload / Infinity

- 把 optimizer state offload 到 CPU 内存
- 把 param 也 offload 到 NVMe（disk）
- 小集群训大模型用，**速度大幅下降**（CPU → GPU bandwidth ~30 GB/s 远低于 HBM 3 TB/s），仅 hobbyist 用

### 2.6 ZeRO 与 FSDP 区别

- **ZeRO**：DeepSpeed 实现，3 个 stage，配置灵活
- **FSDP**：PyTorch 官方，等价 ZeRO-3，集成 autograd hook 更紧
- 2024+ 工业默认 **FSDP**（HF Accelerate / TorchTitan / Megatron-FSDP 都基于它）

## 三、Tensor Parallel (TP)

[Megatron-LM (Shoeybi 2019)](https://arxiv.org/abs/1909.08053)

> 把单个矩阵乘法 W ∈ ℝ^(d×d) 横切或竖切，多卡同时算一部分。

### 3.1 FFN 的 TP 切法（最经典）

考虑 SwiGLU FFN（Llama 风格）：

$$
Y = (\text{SiLU}(X W_\text{gate}) \odot X W_\text{up}) W_\text{down}
$$

- $W_\text{gate}, W_\text{up} \in \mathbb{R}^{d \times 4d}$ → **按列切**（output dim 切）
- $W_\text{down} \in \mathbb{R}^{4d \times d}$ → **按行切**（input dim 切）

```
                                                      AllReduce
X ─┬─→ GPU0: X·W_gate^(1), X·W_up^(1) → SiLU·odot → ·W_down^(1) ─┐
   │                                                              ├─→ Y
   └─→ GPU1: X·W_gate^(2), X·W_up^(2) → SiLU·odot → ·W_down^(2) ─┘
```

**关键洞察**：列切 + 行切的组合让"中间结果不需要通信"——只在最后 W_down 之后做一次 AllReduce 把 partial sum 加起来。

每 transformer block **2 次 AllReduce**（一次 attention 后、一次 FFN 后）。

### 3.2 Attention 的 TP 切法 + GQA 特殊处理

按 head 切：每张 GPU 负责 $N_h / \text{TP}$ 个 head。

**MHA**（Llama-2 风格）：每 GPU 各算自己 head 的 QKV，O 投影按行切。简单。

**GQA / MQA**（Llama-3 / DeepSeek 风格）：

KV head 数 $N_{kv} < N_h$（如 Llama-3 70B：$N_h = 64, N_{kv} = 8$）。

- 若 $\text{TP} \le N_{kv}$（如 TP=8）：KV head 也能均分，每卡 $N_h/8 = 8$ Q head + $N_{kv}/8 = 1$ KV head ✅
- 若 $\text{TP} > N_{kv}$（如 TP=16）：KV head 不够分 → 必须 **replicate KV head**（多卡共享同一组 KV），通信 + 显存有损耗

→ 这是 Llama-3 70B TP 上限 = 8 的原因（NVLink 8 卡 + KV head = 8 完美匹配）。

### 3.3 TP 通信特性

- 通信粒度：layer 内（fine-grained），**每个 forward / backward 都要 AllReduce**
- 必须 **NVLink 级别**带宽才不卡（900 GB/s vs IB 100 GB/s = 9×）
- 工业：**TP ≤ 8**（单机 8 卡 NVLink）
- TP > 8 跨机：通信极慢，几乎不用
- DeepSeek-V3 用 **TP=1**（用 EP 取代分散显存的角色）

### 3.4 Sequence Parallel (SP) 详解

[Megatron-SP (Korthikanti 2022)](https://arxiv.org/abs/2205.05198)：TP 的"延伸"。

**问题**：TP 之后，LayerNorm / Dropout / 残差加法这些 elementwise 算子仍在"完整 seq × 完整 hidden"上做 → 每卡都重复算一遍，显存浪费。

**SP 的切法**：把这些 elementwise 算子沿 **sequence 维度**再切一刀：

```
完整流程：
  X (S × d, BF16)
    │
    ├─→ LayerNorm (按 seq 切, 每卡 S/TP × d)        ← SP 区域
    │      ↓ AllGather (集齐 full seq, 准备 TP)
    ├─→ Attention (按 head 切, full seq × d/TP)     ← TP 区域
    │      ↓ ReduceScatter (按 seq 切回)
    ├─→ LayerNorm + Dropout (按 seq 切)             ← SP 区域
    │      ↓ AllGather
    ├─→ FFN (按 hidden 切)                          ← TP 区域
    │      ↓ ReduceScatter
    └─→ Residual (按 seq 切)                        ← SP 区域
```

**通信总量**：AllReduce → AllGather + ReduceScatter（数学上等价，总流量不变）。

**显存收益**：activation 减 **TP 倍**（之前 elementwise 区域是完整的，现在也切 TP 份）。

→ SP 几乎是 TP 的"免费午餐"，工业默认开（Megatron-LM、TorchTitan 默认）。

### 3.5 TP + SP 通信 overlap

进阶优化（Megatron 2024 Async TP）：

```
TP AllReduce 拆成 ReduceScatter + AllGather
  ↓
ReduceScatter 与下一个 layer 的 LayerNorm 计算 overlap
AllGather 与上一个 layer 的 backward 计算 overlap
```

实测可把 TP 通信开销从 ~25% 降到 ~10%。

## 四、Pipeline Parallel (PP)

> 把模型按 layer 切成 stage，stage 间用点对点通信传 activation。

### 4.1 朴素 PP 的 bubble（GPipe）

```
                                                              
                  ┌───── forward ──────┬──── backward ────┐  
Stage 0: │F0│F1│F2│F3│                │            │B3│B2│B1│B0│        
Stage 1: │  │F0│F1│F2│F3│             │         │B3│B2│B1│B0│           
Stage 2: │  │  │F0│F1│F2│F3│          │      │B3│B2│B1│B0│              
Stage 3: │  │  │  │F0│F1│F2│F3│       │   │B3│B2│B1│B0│                 
                                  ↑      ↑                              
                                  warmup bubble  cooldown bubble        
```

bubble 比例 $= (P-1) / (P + M - 1)$，$P=$ stage 数，$M=$ micro-batch 数。

P=4, M=4: bubble = 3/7 ≈ 43% 浪费
P=4, M=32: bubble = 3/35 ≈ 8%

→ 想缩小 bubble：**micro-batch 多**或用更精细 schedule。

### 4.2 1F1B (PipeDream)

[Narayanan 2019](https://arxiv.org/abs/1806.03377)：交替执行 1 forward + 1 backward。

```
Stage 0: │F0│F1│F2│F3│B0│F4│B1│F5│B2│F6│B3│F7│B4│B5│B6│B7│
Stage 1: │  │F0│F1│F2│B0│F3│B1│F4│B2│F5│B3│F6│B4│F7│B5│B6│B7│
Stage 2: │  │  │F0│F1│B0│F2│B1│F3│B2│F4│B3│F5│B4│F6│B5│F7│B6│B7│
Stage 3: │  │  │  │F0│B0│F1│B1│F2│B2│F3│B3│F4│B4│F5│B5│F6│B6│F7│B7│
                  ↑ steady state 开始
```

**优点**：
- bubble 仍 $(P-1)/(P+M-1)$，但**每个 micro-batch 的 activation 一旦 backward 完成就释放**
- → activation 显存减 ~P×（vs GPipe 保留全部 micro-batch 的 activation）

工业默认调度（Megatron、DeepSpeed、TorchTitan 都用）。

### 4.3 Interleaved 1F1B (Megatron Virtual Pipeline)

[Megatron-LM v2 (Narayanan 2021)](https://arxiv.org/abs/2104.04473)：每个 stage 持有 **多个 chunk**（"虚拟 stage"）。

```
原始：4 stage × 24 layer/stage = 96 layer
Interleaved (V=4 chunks/stage):
  Stage 0 持有 layer [0-5, 24-29, 48-53, 72-77]
  Stage 1 持有 layer [6-11, 30-35, 54-59, 78-83]
  Stage 2 持有 layer [12-17, 36-41, 60-65, 84-89]
  Stage 3 持有 layer [18-23, 42-47, 66-71, 90-95]
```

每个 micro-batch 在 stage 间走 4 个来回 → 通信增加 4×，但 bubble 减少到 $(P-1)/(P \cdot V + M - 1)$。

V=4: bubble 减 4×。代价：跨 stage P2P 通信多 4×（IB 通常够用，不是瓶颈）。

Llama-3 训练用了 Interleaved 1F1B。

### 4.4 Zero Bubble PP

[Zero Bubble PP (Qi 2024)](https://arxiv.org/abs/2401.10241)：把 backward 拆成两部分。

```
经典 backward(B):  
  B_input  = ∂L/∂x_input    ← 需要前向传输完成才能开始
  B_weight = ∂L/∂W          ← 与 B_input 同时算，但其实"等下一个 micro-batch 时再算也行"
```

**洞察**：B_weight 不在关键路径上（只是为了 optimizer.step），可以**延后执行**填到 bubble 里。

```
Stage 0: │F0│F1│F2│F3│Bi0│F4│Bi1│F5│Bi2│F6│Bi3│F7│Bi4│Bi5│Bi6│Bi7│
                                                              │  Bw0│Bw1│Bw2│Bw3│Bw4│Bw5│Bw6│Bw7│
        ↑ 关键路径 (forward + B_input)                              ↑ B_weight 填到 cooldown bubble 里
```

bubble 几乎为 0（理论 0%，实际 ~5% due to schedule overhead）。

### 4.5 DualPipe (DeepSeek-V3)

[DSv3 §3.2.2](https://arxiv.org/abs/2412.19437) 提出：**双向 pipeline**，前向后向同时跑。

```
朴素 PP 是「单向」：micro-batch 从 stage 0 → P-1 (forward) → P-1 → 0 (backward)

DualPipe 是「双向」：
  奇数 micro-batch 从 stage 0 → P-1 → 0     (forward → backward)
  偶数 micro-batch 从 stage P-1 → 0 → P-1  (forward → backward, 反方向)
  
  两个方向的 micro-batch 在 stage 中间相遇 → 互相填 bubble
```

效果：
- bubble ≈ 0（双向流水互补）
- 通信用 **2 个 stream**（NVLink P2P 双向带宽都跑满）
- 与 EP All-to-All overlap 配合（DSv3 的 EP 通信也是双向）

代价：
- 每 stage 显存 ×2（两个方向的 in-flight activation 都要存）
- 实现复杂（DSv3 自研 schedule）

### 4.6 PP 通信

- 每 stage 边界发 activation（forward）+ gradient（backward）
- 通信量小（仅 activation tensor，$B \cdot S \cdot d$ bytes），**跨机 InfiniBand 即可**
- 适合大模型纵向扩展（PP=8、16 常见）

### 4.7 PP 显存

- 每 stage 只存 1/P 模型 → 大模型必备
- 但要存 **in-flight micro-batch 的 activation** → activation checkpointing 几乎必开（§9）

### 4.8 PP 调度对比汇总

| schedule | bubble | activation 显存 | 通信 | 代表 |
|---------|--------|---------------|------|------|
| GPipe (2018) | $(P-1)/M$ | $M \times$ stage act | 标准 P2P | 早期 |
| **1F1B** | $(P-1)/M$ | $P \times$ stage act | 标准 P2P | 工业默认 |
| **Interleaved 1F1B** | $(P-1)/(P \cdot V \cdot M)$ | $P \times V$ act | $V \times$ P2P | Megatron, Llama-3 |
| **Zero Bubble PP** | ~0 | $P \times$ act | 同 1F1B | 新潮 (2024) |
| **DualPipe** | ~0 | $2P \times$ act | 2× 双向 stream | DSv3 |

## 五、Expert Parallel (EP)

详见 §9.4。简述：

```
EP:  把 N 个 expert 分到 N/EP 卡上，每 token 通过 All-to-All 发送到目标 expert。
```

- 与 TP 互斥（不能既切 expert 又切 expert 内 GEMM）
- 与 DP / PP / SP 兼容
- DeepSeek-V3: EP=64 跨 8 节点

通信特点：
- **2 次 All-to-All per layer**（dispatch + combine）
- All-to-All 是"反对角"通信，每对节点都要发数据 → 跨机 IB 网络是瓶颈
- DSv3 用 **Node-Limited Routing** 把每 token 限制最多去 4 个节点（减扇出）

## 六、Context Parallel (CP)

> Sequence 过长（>128K），单卡 activation 都存不下。沿 seq 维度切。

### 6.1 Ring Attention

[Ring Attention (Liu 2023)](https://arxiv.org/abs/2310.01889)：

```
GPU0: tokens[0:32k]    Q0, K0, V0
GPU1: tokens[32k:64k]  Q1, K1, V1
GPU2: tokens[64k:96k]  Q2, K2, V2
GPU3: tokens[96k:128k] Q3, K3, V3

Step 1: 每 GPU 用自己的 Q 算 attention(Q_i, K_i, V_i) （local block）
Step 2: K/V 沿 ring 传到下一个 GPU
Step 3: 每 GPU 算 attention(Q_i, K_{i-1}, V_{i-1}) 累加
Step 4: 重复 ring rotation N-1 次，凑齐所有 K/V
```

通信：每 step 沿 ring 发一份 K/V，总通信量 $O(S)$。**Q 不动**，通信少一半。

通过 **FlashAttention** 的 online softmax 数学，能正确 reduce 不同 KV chunk 的 attention 结果（详 §6）。

### 6.2 Causal Mask 下的 Load Balance

朴素 Ring Attention 在 causal mask 下有严重不均：

```
GPU0 (tokens 0~31k):     算 4 个 KV chunk 的 attention (全可见)
GPU3 (tokens 96k~128k):  只能算自己这一段（causal mask 截断后面）
```

→ 末端 GPU 算 N/N = 1× 工作量，开头 GPU 算 1/N 工作量。负载不均。

**Striped Attention / Zigzag Attention**：用条带式的 token 分配，让每 GPU 的计算量大致相等。

```
朴素分配:    GPU0: [0-31k]      GPU1: [32k-63k]    GPU2: [64k-95k]    GPU3: [96k-128k]
Striped:    GPU0: [0,4,8,...]  GPU1: [1,5,9,...]  GPU2: [2,6,10,...] GPU3: [3,7,11,...]
```

→ 每 GPU 持有的 token 跨越整个 seq，causal mask 下计算量均匀。

Llama-3 训 128K context 用 Striped + Ring。

### 6.3 应用

- Llama-3 训练 128K context 用 CP=8
- Gemini 1.5 / Kimi K2 等长 context 模型必备
- 推理时也可用（详见 §12）

详见 §8（长上下文章节）。

## 七、5D / 7D 并行的物理拓扑映射 ★（实战核心）

5D rank 怎么映射到 NVLink / IB / 跨机架的物理拓扑？这是大集群训练的最关键决策之一。

### 7.1 物理层级与带宽

```
┌─────────────────────────────────────────────────────────────┐
│ HBM (single GPU): 3 TB/s          ← 单卡内                 │
│ NVLink within node (8 GPU): 900 GB/s     ← 节点内 NVLink   │
│ InfiniBand HDR/NDR: 50-100 GB/s       ← 跨节点（同机架）   │
│ Cross-rack (Spine switch): 25-50 GB/s   ← 跨机架           │
│ Cross-datacenter: < 10 GB/s           ← 极慢，几乎不并行  │
└─────────────────────────────────────────────────────────────┘
```

→ 通信频繁的维度（TP）必须放在快通道上（NVLink），通信稀疏的（DP）可以走慢通道（IB）。

### 7.2 选型经验法则

```
维度       通信频率/层   单次通信量    建议物理位置
─────────────────────────────────────────────────────
TP         每 layer 2 次  全 hidden    NVLink 内 ★
SP         随 TP          中等         同 TP
EP         每 MoE layer   token batch  NVLink 优先, 否则 IB
PP         每 stage 边界  activation   IB 即可
CP         每 attention   K/V chunk    NVLink 优先
DP / FSDP  每 step        full grad    任何
```

### 7.3 DeepSeek-V3 配置（671B，2048+ H800）

```
DP = 16          (跨 16 个"DP group")
PP = 16          (DualPipe schedule, near-zero bubble)
EP = 64          (MoE expert 切到 64 路)
TP = 1           (没用 TP, 因 EP 已足够分散显存)
SP = 1           (与 TP 配对)
ZeRO-1           (仅 optim state 分片)
CP = 1           (训练时 context 4K-128K，没必要)

总卡数 = DP × PP × EP / (EP within DP) = 16 × 16 × 8 = 2048

物理映射:
  EP=64 横跨 8 个节点 (8 卡/节点)
        ← Node-Limited Routing 限制每 token 最多去 4 个节点
  PP=16 沿 IB 切 16 stage
  DP=16 跨 16 个 PP-EP 子集，AllReduce 走 IB
```

### 7.4 Llama-3.1 405B 配置（16384 卡 H100）

```
DP (FSDP) = 16   (256-rank shard 太大，做 HSDP)
TP = 8           (单机 8 卡 NVLink，匹配 GQA KV head)
SP = enabled     (与 TP 配)
PP = 16          (Interleaved 1F1B, V=4)
CP = 8           (训 128K 时用)

总卡数 = DP × TP × PP × CP = 16 × 8 × 16 × 8 = 16384

物理映射:
  TP=8 节点内 NVLink                  ← 1 节点
  CP=8 (训长 context 时启用)          ← 1-8 节点视情况
  PP=16 跨 IB                         ← 16 节点
  DP=16 (FSDP) 跨整个集群             ← 全集群 AllGather
```

### 7.5 通用选型表

```
单机 ≤ 8 卡:   DP + ZeRO-3 (FSDP) 就够
8-64 卡:       DP + TP=8 + ZeRO-1
64-512 卡:     DP + TP=8 + PP=4-8
512+ 卡:       DP + TP + PP + (EP / CP)
万卡:          5D-7D 全开

模型类型分支:
  Dense (Llama-3):    必须用 TP（70B+ 单 stage 装不下）
  MoE (DSv3):         EP 取代大部分 TP 功能
  长 context (>32K):  CP 必开
```

## 八、通信-计算 overlap ★（决定 MFU 上限）

不做 overlap 的话，通信开销可占总时间 20-40%。工业实战 MFU 50%+ 几乎都靠 overlap。

### 8.1 FSDP forward / backward prefetch

```
正常 forward:  [AG(L)] [F(L)]                    [AG(L+1)] [F(L+1)]
                ↑通信 ↑计算
带 prefetch:   [AG(L)] [F(L)]
                       [AG(L+1)]  ← 在 F(L) 期间发起
                                 [F(L+1)]
```

PyTorch FSDP 默认开启 prefetch，几乎完全 hide 掉 AllGather。

### 8.2 TP All-Reduce overlap (Async TP)

Megatron-LM 2024 引入的 Async TP：

```
TP AllReduce 拆成 ReduceScatter + AllGather
  └ ReduceScatter 与下一个 layer 的 LayerNorm overlap
  └ AllGather 与上一个 layer 的 backward overlap
```

### 8.3 PP warmup / cooldown overlap

1F1B 调度本身就是 overlap 的体现：steady state 时 stage 间通信和计算完全 pipeline。

### 8.4 EP All-to-All overlap (DualPipe 关键)

DSv3 的双向流水：

```
正常 EP forward:  [A2A dispatch] [expert compute] [A2A combine]
                    ↑ 网络通信      ↑ GPU 计算      ↑ 网络通信

DualPipe:
  forward direction:  [A2A_d_1] [expert_1] [A2A_c_1]
  backward direction: [A2A_d_2] [expert_2] [A2A_c_2]
                                                ↑ 两方向通信 / 计算交错填空
```

实测 DSv3 在 H800 上把 EP 通信开销从 ~30% 降到 ~5%。

### 8.5 Activation checkpointing 与 overlap

ckpt 的 recompute 也可以与下一个 layer 的 AllGather overlap。TorchTitan / Megatron 都已支持。

## 九、Activation Checkpointing 精算

> 不存中间 activation，反向时 recompute。

```
forward:     存 layer 0, 5, 10, ...  (每 N 层一个 ckpt)
backward:    用最近 ckpt 重新 forward 拿到 activation，再 backward
```

### 9.1 显存 / 算力 trade-off

- **显存减 ~5-10×**
- **算力多 ~30%**（多一次 forward）
- 工业训练必开。**SP + ckpt + ZeRO 是显存三件套**。

### 9.2 Selective Checkpointing — 算清账才能选对

不同算子的 "activation memory / FLOPs" 比率差异巨大：

| 算子 | activation 显存 | FLOPs | mem/FLOPs 比 | 是否值得 ckpt |
|------|---------------|-------|-------------|-------------|
| Attention QK^T | 大 ($O(S^2)$) | $2 B S^2 d$ | 高 | ❌（FlashAttn 已 mem-efficient） |
| Attention softmax | 大 ($O(S^2)$) | $O(BS^2)$ | 极高 | ✅（recompute 便宜） |
| FFN（4d 升维）| 中 ($4 d$) | 大 | 低 | ❌（recompute 贵） |
| LayerNorm | 小 | 小 | 中 | ✅（recompute 几乎免费） |
| Dropout | 小 | 微 | 中 | ✅ |

**Megatron 的 "selective recompute attention only"**：

```
策略 1: full ckpt：每 N 层全 ckpt → 显存最省，算力 +33%
策略 2: selective: 只 ckpt attention 块（softmax + dropout）→ 显存省 ~70%，算力仅 +5%
```

→ 工业选 selective + FlashAttn。

### 9.3 与 FlashAttention 的配合

FlashAttn 本身就是 "**recompute attention map in backward**" 的特例：

```
forward:  不存 attention map (S × S), 只存 (Q, K, V) 和 softmax stats
backward: 沿用 stats 重新算 attention map
```

所以**用了 FlashAttn 就不再需要单独 ckpt attention**。Llama-3 的策略：FlashAttn + selective ckpt FFN 入口。

## 十、通信原语速查

| 原语 | 含义 | 用例 |
|------|------|------|
| **AllReduce** | 所有节点 reduce 后广播 | DDP grad、TP block 末 |
| **AllGather** | 所有节点拼到所有节点 | ZeRO-3 / FSDP param 收集 |
| **ReduceScatter** | reduce 后只分片到各节点 | ZeRO grad 分片、SP backward |
| **All-to-All** | 转置式全交换 | EP dispatch / combine |
| **Send/Recv** | 点对点 | PP 边界 |
| **Broadcast** | 一对多 | 初始化、checkpoint load |

**等价关系**：
- AllReduce ≡ ReduceScatter + AllGather（总流量同）
- All-to-All ≡ N 次 send + N 次 recv（原语层），但硬件优化为单 collective

带宽硬件参考：
- **NVLink 4 / NVSwitch**：~900 GB/s（H100 within node）
- **InfiniBand HDR/NDR**：50-100 GB/s（跨节点）
- **以太网 RDMA**：25-100 GB/s

→ **TP 必须在 NVLink 内、PP 可跨 IB、DP/EP 跨 IB 也可**。

## 十一、关键问答

**Q1**：DP / TP / PP 哪个通信最贵？
- 单 step 通信量：DP ≈ TP（都 AllReduce）> PP（仅点对点）
- 单 step 通信频率：TP（每 layer 2 次）> PP（每 stage 边界）> DP（每 step 1 次）
- 经验：**TP 必须 NVLink，PP 可跨机，DP 跨机也可**

**Q2**：FSDP 与 ZeRO-3 完全等价吗？
- 数学上等价
- 实现：FSDP 集成 autograd 更紧，hook 更轻；DeepSpeed ZeRO 配置更灵活
- 2024+ 推荐 FSDP（PyTorch 官方，TorchTitan 默认）

**Q3**：DeepSeek-V3 为什么不用 TP？
- TP 通信粒度细 + 必须 NVLink 8 卡内
- 用 EP 已经分散显存
- TP=1 让单节点 8 卡都参与 EP / DP，集群利用率高
- 节省了 TP allreduce 流量

**Q4**：什么时候必须用 PP？
- 模型层数大（70B+ 30+ 层）+ 单 stage 显存放不下
- 跨节点扩展时，比起 TP 通信更友好
- PP 唯一缺点 = bubble，但有 DualPipe / Zero Bubble 缓解

**Q5**：activation checkpointing 必开吗？
- 长 context、大 batch、大模型 → 必开
- 短 context（< 2K）、小模型 → 可选关闭
- 用 FlashAttn 后可以"selective ckpt"，性价比最高

**Q6**：为什么 Llama-3 用 TP=8 而 DeepSeek-V3 用 TP=1？
- Llama-3 是 dense → 没有 EP 这条切割维度 → 必须 TP+PP+CP 切显存
- DeepSeek-V3 是 MoE → EP 已经替代了大部分 TP 功能
- 同时 Llama-3 70B 的 KV head = 8 与 TP=8 完美匹配（GQA）

**Q7**：训练 1B 模型还要并行吗？
- 1-3B：FSDP / ZeRO-3 单机 8 卡足够
- 7B：FSDP + activation ckpt，单机即可
- 13B-30B：FSDP + 多机
- 70B+：必须 PP + TP

**Q8**：Zero Bubble PP 和 DualPipe 哪个更好？
- ZBP：实现相对简单，单向流水，与 1F1B 兼容
- DualPipe：实现复杂，需要 2× 显存（in-flight act 双倍）
- 工业：dense 用 ZBP，MoE 用 DualPipe（DSv3 因 EP 通信大才需要 DualPipe 的双向通信）

**Q9**：HSDP 比纯 FSDP 好多少？
- 节点内 FSDP（NVLink 快）+ 节点间 DDP（IB 慢但 step 末才 reduce）
- 通常 1.3-1.8× 吞吐（取决于跨机带宽与模型大小）
- 代价：节点内 replicate factor 倍显存冗余（如 8 节点 = 8× state）
- 适合：跨机 IB 不富裕的集群（多数云上集群）

**Q10**：5D 并行嵌套时，rank 顺序怎么排？
- 标准：`global_rank = ((dp_rank * pp_size + pp_rank) * tp_size + tp_rank)`
- 物理上：**TP rank 必须连续放在同一节点**（NVLink），PP / DP 跨节点
- TorchTitan / Megatron 默认按此 layout

**Q11**：Ring Attention 在 causal mask 下负载怎么均衡？
- 朴素：尾端 GPU 算量 = N×开头 GPU
- 解决：Striped / Zigzag 分配（token 跨 GPU 交错），每 GPU 持有"覆盖整 seq 的 1/N"
- Llama-3 用了 Striped Ring Attention

**Q12**：FP8 + 并行有什么注意点？
- TP AllReduce 走 FP8 → 累加误差大，需谨慎
- ZeRO/FSDP AllGather param 用 BF16（param 量小，精度优先）
- ReduceScatter grad 可走 FP8（DSv3 实测稳定）
- EP All-to-All 走 FP8（token 量大，省带宽关键）
