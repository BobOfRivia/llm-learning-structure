# 12.5 长上下文推理（位置外推 + KV 量化 + KV 驱逐 + Chunked Prefill）

[← 返回框架](../../README.md) · [📎 materials.md → §12.5](../../materials.md) · 承接 [§8 长上下文（训练+外推）](../08-长上下文/)

## 〇、本节回答什么

> §8 讲了**怎么训出一个长上下文模型**（curriculum + 位置编码外推）；本节讲**怎么把它推理跑起来**。100K–1M 上下文推理的三大瓶颈：（1）KV cache 显存爆炸；（2）prefill 时间 $O(N^2)$；（3）位置编码外推误差累积。本节按 **KV 量化 → KV 驱逐 → chunked prefill → prefill 并行 / SSA / chunk attention → 位置外推工程** 顺序梳理。

长上下文推理是 2024–2025 工业最棘手的问题之一。Gemini 1M、Claude 1M、Kimi 2M、GLM 2M、Qwen2.5 1M 都在攻这一线。

---

## 一、长上下文推理的三大瓶颈

### 1.1 KV 显存爆炸（最直接）

```
KV_bytes = 2 × L × H_kv × d_h × T × dtype
```

例：Llama-3-70B（L=80, H_kv=8, d_h=128），FP16：

| 上下文长度 T | KV 大小 / sequence |
|--------------|----------------------|
| 4K | 1.3 GB |
| 32K | 10.5 GB |
| 128K | 42 GB ← 1 张 H100 几乎只能跑 1 个用户 |
| 1M | 328 GB ← 单卡不可行 |

→ 长上下文推理必然需要 **KV 优化**（量化 / 驱逐 / 卸载）。

### 1.2 Prefill 时间 $O(N^2)$

标准 attention 在 prefill 时算 $QK^\top$ 是 $O(N^2 \cdot d)$：
- 4K：0.5s
- 32K：~30s
- 1M：~3 小时（理论值）

→ 必须 **chunked prefill + 稀疏注意力（§6）+ KV reuse**。

### 1.3 位置编码外推

训练上下文 32K 的模型，推理时直接喂 128K，**RoPE 外推会发散**。需要 NTK-aware / YaRN / LongRoPE 等 §8 的方法在推理侧也生效。

## 二、KV 量化（KV Cache Quantization）

### 2.1 现状：FP8 / INT8 / INT4

| 方案 | bits | 质量损失 | 显存压缩 |
|------|------|----------|----------|
| FP16 baseline | 16 | - | 1× |
| **FP8 (E4M3)** | 8 | 几乎无 | 2× |
| INT8 (per-token) | 8 | 很小 | 2× |
| INT4 (per-channel + per-token 混合) | 4 | 长上下文有累积误差 | 4× |
| 2-bit (KIVI) | 2 | 需精心 calibration | 8× |

> 2024–2025 工业默认 **KV FP8**，质量几乎无损，vLLM / TensorRT-LLM 都直接开。

### 2.2 KIVI（NeurIPS 2024）：2-bit KV 的代表

核心观察：
- **K 在 channel 维度有 outlier**：用 **per-channel** 量化
- **V 在 token 维度均匀**：用 **per-token** 量化

→ **K per-channel + V per-token** 的非对称 2-bit 量化，长上下文 needle test 几乎无损。

### 2.3 KV 量化的累积误差

K/V 在 decode 阶段持续被读取，量化误差通过 attention 反复传播。短上下文影响小，**长上下文（> 100K）必须验证 needle / RULER 等评测**。一般经验：FP8 在 1M 以下完全 OK，INT4 在 32K 以上要谨慎。

## 三、KV 驱逐（KV Eviction）：丢掉一部分 KV

> 与量化正交：量化是降单位精度，驱逐是降 token 数。

### 3.1 直觉

attention map 的稀疏性是已被反复观察的事实：**多数 token 的注意力权重接近 0**——保留前几个 + 最近几个 + 一些高 attention 的 token，就能近似原 attention。

### 3.2 几个代表方法

#### 3.2.1 StreamingLLM (2023, MIT)

- 关键发现：**前几个 token 是 "attention sink"**——即使语义无关，attention 仍大量集中在序列开头几个 token
- 保留方案：**头部 4 个 sink token + 最近 W 个 token**，中间全部驱逐
- 适用：聊天等"短记忆"场景，可支撑无限滚动

#### 3.2.2 H2O（Heavy Hitter Oracle, NeurIPS 2023）

- **关键观察**：少量"heavy hitter" token 承担了大部分 attention 质量
- 维护一个 budget B 的窗口，按累积 attention score 留 top-B
- 在生成任务上接近全 KV 的质量

#### 3.2.3 SnapKV（2024）

- prompt 太长且大多无用 → 用 **prompt 末尾的 query 找出 prompt 中重要的 token**，只保留它们的 KV
- 适合**长 prompt + 短 output** 的 RAG / 长文档 QA
- 实测 32K → 4K KV 几乎无损，4× 显存压缩

#### 3.2.4 PyramidKV / PyramidInfer

- 上层 layer 需要的 token 比下层少 → **不同 layer 用不同 KV budget**（金字塔）
- 更精细的资源分配

### 3.3 驱逐的代价

- 长链推理（CoT）容易丢中间步骤
- 需要细粒度的 budget 调度
- 通用模型上线开 H2O / SnapKV 前必须 needle benchmark 验证

## 四、Chunked Prefill（长 prompt 的关键）

### 4.1 朴素 prefill 的痛点

1M token prompt 一次性算 $QK^\top$：
- 算力上 N^2 / d × FLOPs，几小时
- 显存上 attention matrix 中间结果 N^2 × bytes 不可承受
- batch 内其他请求被冻结

### 4.2 chunked prefill = 分块 + flow

把 prompt 切成 chunk_size $C$（典型 512 / 2048 / 8192）：

```
chunk 1:  [t1..tC]   ─ forward, 写入 KV pool
chunk 2:  [tC+1..2C] ─ forward, 看到 chunk1 的 KV
chunk 3:  ...

每个 chunk 内部仍是标准 FlashAttention
跨 chunk 通过 KV 读取
```

效果：
- 每个 chunk 是合理大小的 forward，可与 decode 拼 batch
- 不需要 N^2 显存
- 与 PagedAttention 完美配合

> chunked prefill 已是所有主流 serving 系统默认开启。

### 4.3 chunk 大小的 trade-off

- chunk 小（512）→ launch overhead 大，prefill 慢，但 decode 抖动小
- chunk 大（8192）→ prefill 快，但 decode TPOT 抖动
- 动态：根据 batch 中 decode 请求数量自适应调

## 五、稀疏注意力 / SSA（结构稀疏）：让 prefill 跳过无用计算

> 这一节与 §6 重叠，本节聚焦推理侧实战。

### 5.1 Streaming + 稀疏

很多 24K+ 长 prompt 中，远距离 token 的 attention 稀疏程度极高（< 1% 非零）。**长上下文推理可以用结构稀疏直接跳过大量 attention block**。

### 5.2 NSA / DSA（DeepSeek 派）

- **NSA**（Native Sparse Attention, DeepSeek 2025-02）：训练时就是稀疏的，推理时按 top-k 的 block 计算
- **DSA**（V3.2, 2025-09）：Lightning Indexer + 细粒度 token-level top-k
- **CSA + HCA**（V4, 2026-04）：分层压缩 attention，HCA 把 128 token 压成 1 个 entry

这些方案让 **prefill 时间从 $O(N^2)$ 降到接近 $O(N \log N)$ 或 $O(N \cdot k)$**。

### 5.3 推理侧的稀疏注意力（不改训练）

- **MoBA**（Moonshot, 2025）：把 MoE 思路放到 attention block 路由，推理侧近似稀疏 attention
- **MInference**（Microsoft, 2024）：3 种稀疏模式（A-shape / Vertical-Slash / Block-Sparse）按 head 路由

> 推理稀疏一般有 5–20× prefill 加速，质量损失可控（needle 几乎无损）。

## 六、Prefill 并行（Context Parallel + Ring Attention）

### 6.1 单卡显存不够时

128K+ 的 prompt 在单卡 H100 上显存放不下 attention 中间态。**Context Parallel (CP)** / **Ring Attention** 把 sequence 切片到多卡：

```
Card 1: tokens [1..N/4]
Card 2: tokens [N/4..N/2]
Card 3: tokens [N/2..3N/4]
Card 4: tokens [3N/4..N]

attention 时按 ring 传递 KV：
  iter 0: 卡 i 用本地 Q × 本地 K
  iter 1: 卡 i 用本地 Q × 卡 (i+1) 的 K
  ...
```

**Ring Attention** 让通信与计算重叠，理论上无显存上限。

### 6.2 工程实现

- **Megatron-CP**（NVIDIA）
- **Ring Attention** (Liu et al., 2023)
- vLLM 已实验性支持 CP（多机 1M 上下文已可跑）

## 七、位置编码外推（推理侧）

> §8 详细推过 PI / NTK-aware / YaRN / LongRoPE。本节关注推理侧实战。

### 7.1 训练长度 vs 推理长度的 gap

```
训练 8K → 推理 32K：直接喂会发散
训练 8K → 推理 128K：必须用外推方案
训练 32K → 推理 128K：YaRN / LongRoPE 已工程成熟
训练 128K → 推理 1M：通常需要 longrope 或 long fine-tune
```

### 7.2 主流方案速查

| 方法 | 训练参与 | 推理改 | 备注 |
|------|----------|--------|------|
| Position Interpolation (PI) | 一般需 fine-tune | RoPE base × scale | 简单，质量一般 |
| NTK-aware | 训练免费 | RoPE base × scale^(d/(d-2)) | 中等 |
| YaRN | 通常 fine-tune | 分频率分段缩放 + 温度修正 | **2024 工业首选** |
| LongRoPE | fine-tune + 进化搜索 | 不均匀 dim-wise scale | Microsoft Phi-3 用 |

### 7.3 推理时的位置外推与 KV 驱逐的交互

KV 驱逐改了 token 位置布局 → 必须把保留 token 的 position id 重映射成连续，否则位置编码失效。StreamingLLM 等方法本身就是基于 position re-mapping 的。

## 八、KV 卸载（Offload）：HBM 之外的层次

### 8.1 三层层次

```
HBM            ─ 当前 batch 活跃 KV
DRAM           ─ 暂时不访问的 KV，prefetch 回来
SSD / NVMe     ─ 长尾、低频 KV
```

Mooncake 把这一层抽象成集群级 KV pool。单机也能做：

- **CacheGen**（2024）：KV 按重要性分层；近期 token KV → HBM，远期 → DRAM
- **DeepSpeed-FastGen / FlexLLMGen**：CPU offload KV

代价：访问 DRAM 比 HBM 慢 ~20×，SSD 慢 ~1000×；需要 prefetch + overlap。

## 九、长上下文推理"组合拳"实战配方

> 不同长度 / 任务用不同组合。

### 9.1 32K 上下文（常规长上下文）

- KV：FP8 量化
- Prefill：chunked prefill（chunk_size 2048）
- 位置：训练时已含 32K，无需外推
- 估算：单 H100 跑 70B 模型，并发 8–16 路

### 9.2 128K 上下文（RAG / 长文档）

- KV：FP8 + SnapKV（保留最重要的 16K）或 H2O
- Prefill：chunked prefill + 稀疏注意力（MInference）
- 位置：YaRN / LongRoPE
- 估算：单 H100 跑 70B 并发 1–2 路；多卡 PD 分离更优

### 9.3 1M 上下文（前沿）

- KV：FP8 + StreamingLLM-style sink token + 驱逐
- Prefill：Ring Attention / Context Parallel + 稀疏（NSA / MoBA）
- 位置：LongRoPE + long-context fine-tune
- 估算：单卡不可行；至少 8 卡 H200 / DGX

## 十、关键问答

**Q1：KV FP8 和 weight FP8 是同一件事吗？**
A：不是。weight FP8 影响**所有阶段**（prefill + decode）的 GEMM；KV FP8 只影响 **decode 阶段读取 K/V 的 attention kernel** 和**显存大小**。两者数学独立、可叠加。一般工业生产会同时开。

**Q2：H2O / SnapKV / StreamingLLM 选哪个？**
A：取决于负载。**StreamingLLM** 适合无限滚动聊天（短记忆）；**H2O** 适合通用长生成；**SnapKV** 适合长 prompt + 短 output（RAG、文档摘要 QA）。SnapKV 在 RAG-like 上 4×+ KV 压缩几乎无损，最实用。

**Q3：Chunked prefill 把 1M prompt 切成多少 chunk 合适？**
A：chunk_size 通常 2048–8192。1M / 2048 = 488 chunk，仍然是合理的 forward 数量。chunk 太小 launch overhead 大，太大与 decode 抢资源。生产里**动态调**：batch 内 decode 请求多就缩小 chunk，纯 prefill 阶段放大 chunk。

**Q4：为什么 attention sink（StreamingLLM 发现的）存在？**
A：softmax 必须总归一化到 1——当模型不想"看"任何位置时，会把无意义的 weight 倾倒到序列开头几个 token（"垃圾桶"）。这是 softmax 的数学结构副产物，所有 decoder-only LLM 都有。删了 sink token 会让所有后续 token 的 attention 分布失衡。一些新模型设计（如 Cohere）引入显式 sink token。

**Q5：YaRN 比 NTK-aware 好在哪？**
A：（1）YaRN 引入**分频率分段缩放**——低频维度（语义大尺度）插值更激进，高频维度（细节）几乎不变；（2）YaRN 还修正了 attention 的温度（scale by $\sqrt{1/0.07 \cdot \log s}$），补偿稀释效应。结果：在更长上下文下质量明显优于 NTK-aware。

**Q6：1M 上下文真的有用还是 marketing？**
A：(1) **长文档摘要 / 法律 / 医学**——真实需求；(2) **代码 repo 全局理解**——真实需求，Cursor / Claude Code 已重度使用；(3) **needle test 性能** ≠ **真实长上下文推理质量**——很多模型 needle 100% 但 RULER / multi-hop QA 仍然差。所以 1M 的 "useful长度" 通常 < 实际声称的窗口大小。

**Q7：长上下文推理为什么常用 PD 分离？**
A：长上下文 prefill 极重（$O(N^2)$ FLOPs + 大显存峰值），适合放在 compute-rich 节点；decode 阶段反而**KV 大但 FLOPs 小**，适合放在 bandwidth-rich + 大显存节点（甚至 H200 / GH200）。同节点跑两者会严重冲突——这是 §12.4 PD 分离思路的延伸。
