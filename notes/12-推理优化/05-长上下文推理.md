## 〇、本节回答什么

> §8 讲了**怎么训出一个长上下文模型**（curriculum + 位置编码外推）；本节讲**怎么把它推理跑起来**。100K–1M 上下文推理的三大瓶颈：（1）KV cache 显存爆炸；（2）prefill 时间 $O(N^2)$；（3）位置编码外推误差累积。本节按 **KV 量化 → KV 驱逐 → chunked prefill → prefill 并行 / SSA / chunk attention → 位置外推工程** 顺序梳理。

长上下文推理是 2024–2025 工业最棘手的问题之一。Gemini 1M、Claude 1M、Kimi 2M、GLM 2M、Qwen2.5 1M 都在攻这一线。

---

## 一、长上下文推理的三大瓶颈

### 1.1 KV 显存爆炸（最直接）

```
KV_bytes = 2 × L × H_kv × d_h × T × dtype
```

例：Llama-3-70B（L=80, H_kv=8, d_h=128），FP16：

| 上下文长度 T | KV 大小 / sequence |
|--------------|----------------------|
| 4K | 1.3 GB |
| 32K | 10.5 GB |
| 128K | 42 GB ← 1 张 H100 几乎只能跑 1 个用户 |
| 1M | 328 GB ← 单卡不可行 |

→ 长上下文推理必然需要 **KV 优化**（量化 / 驱逐 / 卸载）。

### 1.2 Prefill 时间 $O(N^2)$

标准 attention 在 prefill 时算 $QK^\top$ 是 $O(N^2 \cdot d)$：
- 4K：0.5s
- 32K：~30s
- 1M：~3 小时（理论值）

→ 必须 **chunked prefill + 稀疏注意力（§6）+ KV reuse**。

### 1.3 位置编码外推

训练上下文 32K 的模型，推理时直接喂 128K，**RoPE 外推会发散**。需要 NTK-aware / YaRN / LongRoPE 等 §8 的方法在推理侧也生效。

## 二、KV 量化（KV Cache Quantization）

### 2.1 现状：FP8 / INT8 / INT4

| 方案 | bits | 质量损失 | 显存压缩 |
|------|------|----------|----------|
| FP16 baseline | 16 | - | 1× |
| **FP8 (E4M3)** | 8 | 几乎无 | 2× |
| INT8 (per-token) | 8 | 很小 | 2× |
| INT4 (per-channel + per-token 混合) | 4 | 长上下文有累积误差 | 4× |
| 2-bit (KIVI) | 2 | 需精心 calibration | 8× |

> 2024–2025 工业默认 **KV FP8**，质量几乎无损，vLLM / TensorRT-LLM 都直接开。

### 2.2 KIVI（NeurIPS 2024）：2-bit KV 的代表

核心观察：
- **K 在 channel 维度有 outlier**：用 **per-channel** 量化
- **V 在 token 维度均匀**：用 **per-token** 量化

→ **K per-channel + V per-token** 的非对称 2-bit 量化，长上下文 needle test 几乎无损。

### 2.3 KV 量化的累积误差

K/V 在 decode 阶段持续被读取，量化误差通过 attention 反复传播。短上下文影响小，**长上下文（> 100K）必须验证 needle / RULER 等评测**。一般经验：FP8 在 1M 以下完全 OK，INT4 在 32K 以上要谨慎。

## 三、KV 驱逐（KV Eviction）：丢掉一部分 KV

> 与量化正交：量化是降单位精度，驱逐是降 token 数。**算法机制详见 [§8.3](../08-长上下文/03-kv节省.md);本节只列工程集成要点。**

### 3.1 算法一览(链接)

| 方法 | 一句话 | 适用 |
|---|---|---|
| **StreamingLLM** | 保留 4 sink token + 最近 W 个 | 流式对话/无限滚动 |
| **H2O** | 按累积 attention 留 heavy hitter | 通用生成,B≈L/8 几乎无损 |
| **SnapKV** | prefill 结束时用 prompt 尾部 query 挑 token | 长 prompt + 短 gen(RAG) |
| **PyramidKV** | 上层 layer budget 比下层小(金字塔) | 精细资源分配 |

→ 算法细节、对比、应用边界见 §8.3。

### 3.2 工程集成要点(serving 侧)

- **vLLM 现状**:H2O、StreamingLLM 已有第三方 patch,SnapKV 主要在 vLLM-fork 出现;尚未进主线默认
- **driver 路径**:KV 驱逐改变 PagedAttention 的 block 引用计数 → 需要 reference-counted block manager 支持
- **Multi-tenant 共存**:不同请求开/不开 eviction 难 batch,通常以请求级 flag 控制
- **可叠加**:eviction + KV 量化 + chunked prefill 三者正交,可同时启用,实测 KV 总压缩 8-32×

### 3.3 上线前必做的事

- 长链推理(CoT)容易丢中间步骤 → 必须 RULER / Needle-in-a-Haystack 评测
- 通用模型开 H2O / SnapKV 前 needle benchmark 是 hard gate

## 四、Chunked Prefill（长 prompt 的关键）

> 这一节先从一个具体的"翻车场景"切入,然后讲清楚机制、FLOPs 与带宽账、chunk size 的真实 trade-off,以及与 PD 分离的关系。Chunked prefill 是 2024 年后 vLLM / TensorRT-LLM / SGLang 的默认配置,但很多人只知其名不知其细——这恰恰是面试和调优的高频考点。

### 4.1 翻车场景:一个长 prompt 卡死整批 decode

设想线上一个 batch 正在跑 16 路 decode(每个请求每 ~30 ms 出一个 token),此时一个用户提交了 128K 的长 prompt(比如整个 repo 给 Claude Code 看)。

**朴素 prefill(monolithic prefill)的做法是:把 128K 一次性塞进 forward。** 后果:

| 现象 | 数量级 |
|------|--------|
| prefill 那一步算 $Q K^\top$ | $O(N^2 \cdot d)$ FLOPs,128K 上几秒到十几秒 |
| 那一步的 GPU | 100% 算力被 prefill 占满 |
| 同 batch 16 路 decode | 全部冻结等待——TBT 从 30 ms 飙到 5–15 s |
| 用户感受 | 输出"卡顿/吐字停顿" |

这就是 LLM serving 里最经典的 **head-of-line blocking**:长 prefill 把短 decode 挡在身后。Service-level 上两个核心 SLO:

- **TTFT** (Time To First Token):用户看到第一个字的延迟,主要由 prefill 决定
- **TBT / TPOT** (Time Between Tokens / Time Per Output Token):流式输出的字间间隔,由 decode 决定

朴素 prefill 拼命压 TTFT,但任何长 prompt 都会让同 batch 的 TBT 爆炸。**Sarathi-Serve(OSDI 2024)** 的中心论点就是:**这种 trade-off 是伪命题,可以同时打破**。

### 4.2 核心洞察:prefill 与 decode 在算力维度上互补

回顾 [§4.3 prefill vs decode](../04-kvcache-推理经济学/03-prefill-vs-decode.md):

| 阶段 | arithmetic intensity (ops/byte) | GPU 利用率 | bottleneck |
|------|-------------------------------|-----------|-----------|
| prefill (长 prompt) | 200–400 | 接近 100% | compute-bound,tensor core 饱和 |
| decode (单 token) | 60–80 | 20–40% | memory-bound,HBM 带宽瓶颈 |

decode 阶段 GPU 算力大量闲置——既然 tensor core 反正不忙,**为什么不顺路再算一点 prefill**?反过来:既然 prefill 反正不缺算力,**为什么不顺路把 decode 的 KV 读一下、轻量算一下**?

这就是 Sarathi 的关键招式:**hybrid batch**——每个 iteration 拼一个 prefill chunk + 一批 decode token 一起送进 forward。

### 4.3 机制:chunked prefill + decode piggyback

把长 prompt 切成 chunk_size $C$ 个 token 的小块。每个 iteration 的 batch 组成方式叫 **decode-maximal batching**:

```
iter t:   [prefill_chunk_k 的 C 个 token] + [16 个 decode 各 1 个 token]
                  ↑ 占算力                    ↑ 顺风车,延迟近乎零增量
          全部一次 forward,所有 layer 跑完

iter t+1: [prefill_chunk_(k+1) 的 C 个 token] + [16 个 decode 各 1 个 token]
                                            (16 个 decode 已经多吐了一个 token)
```

调度上有一个统一的 **token budget**(vLLM 叫 `max_num_batched_tokens`,TRT-LLM 叫 `max_num_tokens`),约束每个 iteration 总 token 数:

$$
C + \sum_i \text{decode}_i \le \text{token\_budget}
$$

例如 budget = 2048,batch 内有 16 路 decode,那么 chunk size 自动 = 2048 − 16 = 2032。

**关键效果:**

- 每个 iteration 时长稳定(只跟 token_budget 走),与 prompt 长度脱钩 → **TBT 稳定**
- 长 prompt 的 prefill 摊到 N/C 个 iteration,每一步只占一小段时间 → **decode 不再被冻结**
- prefill chunk 让 tensor core 满载,decode "搭便车"几乎免费(Sarathi 论文里讲 piggyback decode "cost up to an order of magnitude less" 相比独立 decode batch)
- 不再需要为整个 N × N 的 attention matrix 准备显存——peak activation 只跟 C 相关

**实测收益(Sarathi-Serve, OSDI 2024):** Mistral-7B 在单 A100 上 **2.6× throughput**(同 TBT SLO 下),Falcon-180B 在 8×A100 上 **6.9× throughput**。

### 4.4 attention 是怎么算的:FLOPs 不变,带宽变贵

很多人会以为"切 chunk 让 attention 复杂度从 $O(N^2)$ 降下来"——**错**。来算一下账。

**Monolithic prefill** 的 attention(带 causal mask)总 FLOPs:

$$
\text{FLOPs} \approx \frac{N^2}{2} \cdot d
$$

**Chunked prefill** 的 attention:对第 $k$ 个 chunk(包含 $C$ 个 token),它的 Q 要 attend 到 **从开头到当前为止的所有 K/V**——也就是 $kC$ 个位置(其中 $(k-1)C$ 个是历史 chunk,$C$ 个是自己,自己内部还要 causal mask)。求和:

$$
\sum_{k=1}^{N/C} C \cdot kC \cdot d \;\approx\; \frac{N^2}{2} \cdot d
$$

**FLOPs 完全一样**——causal mask 决定的总工作量是物理常数,怎么切都不变。

**但 HBM 带宽不一样**。Monolithic 那一发,K/V tensor 只读一次(FlashAttention 流式访问)。Chunked 之后,第 $k$ 个 chunk 要从 KV pool 把前 $(k-1)C$ 个 token 的 K/V **再读一遍**:

$$
\text{prior KV re-reads} \approx \sum_{k=2}^{N/C} (k-1) C \;=\; \frac{N^2}{2C} \;\;\text{个 token 的 KV}
$$

→ chunk size $C$ 越小,前面 chunk 的 KV 被反复重读次数越多。Sarathi 论文里把这一项叫 "**chunked-prefills 的固有 overhead**",原话:"every subsequent chunk after the first will have to reread all the KV pairs of the prior tokens from GPU memory"。

**直觉公式:** 长上下文里,chunk size $C$ 选 1024 vs 4096,attention 阶段 HBM 读量大约差 4×。这不是 4× 端到端慢,因为 attention 只是整个 forward 的一部分,其他 GEMM(QKV/MLP)和 chunk 数成正比即可——所以 attention reread 的 overhead 一般实测在 **+5%–25%** 量级,远小于 piggyback 带来的 2× 以上吞吐增益。

### 4.5 chunk size(token budget)怎么选

这是 chunked prefill 唯一的核心调参。是一组真实的 trade-off:

| token_budget | TTFT | TBT | prefill 吞吐 | attention reread overhead |
|--------------|------|-----|-------------|---------------------------|
| 256 | 长(更多 iter) | 极稳 | 慢(GPU 不饱和、reread 多) | 大 |
| 512 | 长 | 稳 | 较慢 | 中等 |
| **2048** | 中 | 稳 | 接近峰值 | 小 | ← Sarathi 论文推荐范围 |
| 8192 | 短 | 偶发抖动 | 峰值 | 极小 |
| 不切(monolithic) | 最短 | 长 prompt 时灾难性抖动 | 峰值 | 0 |

**生产常用配置(经验,非官方默认):**

- **vLLM V1**: chunked prefill 默认开。`max_num_batched_tokens` 默认 8192;`long_prefill_token_threshold` 默认 ≈ `max_model_len × 4%`(超过这个长度才走 chunked 路径)。社区报告短模型(8K-32K)用 2048,长上下文(128K+)用 4096–8192
- **TensorRT-LLM**: 提供 dynamic chunk sizing,按 GPU 利用率自动调
- **SGLang**: 类似 vLLM,可手动设

实践建议:**TBT SLO 严的场景(在线对话)选小;TTFT SLO 严或纯长 prompt batch 选大。** 没有"宇宙最优 chunk size"——和模型大小、卡型、TBT/TTFT SLO 直接相关,上线前要 profile。

### 4.6 与 PagedAttention、PD 分离的关系

**与 PagedAttention(§12.3)** 完美正交:chunked prefill 决定 **何时把 KV 写入 KV pool**,PagedAttention 决定 **KV 在物理显存怎么组织**。每个 chunk forward 完就把这 $C$ 个 token 的 KV append 到 paged pool 里,下一个 chunk 自然就能读到。

**与 PD 分离(§12.4)** 是两种不同思路解决同一个问题(prefill 与 decode 冲突):

| | chunked prefill | PD 分离 |
|---|----------------|---------|
| 思路 | 时间维度复用同一组 GPU | 空间维度隔离不同 GPU 集群 |
| 部署复杂度 | 低,单 deployment | 高,需要 KV 跨节点传输(Mooncake/DistServe) |
| TTFT-TBT tradeoff | 受 token_budget 限制,有上限 | 几乎完全解耦,可独立扩 |
| 适用规模 | 中小 cluster、混合负载 | 超大 cluster、长上下文场景 |

**实践组合:** PD 分离架构里,prefill 节点内部还是会用 chunked prefill 来平衡多个并发长 prompt(避免一个 1M 长 prompt 把节点上其他 prompt 都挡住)——所以**两者经常叠加,不是二选一**。

## 五、稀疏注意力 / SSA（结构稀疏）：让 prefill 跳过无用计算

> 这一节与 §6 重叠，本节聚焦推理侧实战。

### 5.1 Streaming + 稀疏

很多 24K+ 长 prompt 中，远距离 token 的 attention 稀疏程度极高（< 1% 非零）。**长上下文推理可以用结构稀疏直接跳过大量 attention block**。

### 5.2 NSA / DSA（DeepSeek 派）

- **NSA**（Native Sparse Attention, DeepSeek 2025-02）：训练时就是稀疏的，推理时按 top-k 的 block 计算
- **DSA**（V3.2, 2025-09）：Lightning Indexer + 细粒度 token-level top-k
- **CSA + HCA**（V4, 2026-04）：分层压缩 attention，HCA 把 128 token 压成 1 个 entry

这些方案让 **prefill 时间从 $O(N^2)$ 降到接近 $O(N \log N)$ 或 $O(N \cdot k)$**。

### 5.3 推理侧的稀疏注意力（不改训练）

- **MoBA**（Moonshot, 2025）：把 MoE 思路放到 attention block 路由，推理侧近似稀疏 attention
- **MInference**（Microsoft, 2024）：3 种稀疏模式（A-shape / Vertical-Slash / Block-Sparse）按 head 路由

> 推理稀疏一般有 5–20× prefill 加速，质量损失可控（needle 几乎无损）。

## 六、Prefill 并行（Context Parallel + Ring Attention）

### 6.1 单卡显存不够时

128K+ 的 prompt 在单卡 H100 上显存放不下 attention 中间态。**Context Parallel (CP)** / **Ring Attention** 把 sequence 切片到多卡：

```
Card 1: tokens [1..N/4]
Card 2: tokens [N/4..N/2]
Card 3: tokens [N/2..3N/4]
Card 4: tokens [3N/4..N]

attention 时按 ring 传递 KV：
  iter 0: 卡 i 用本地 Q × 本地 K
  iter 1: 卡 i 用本地 Q × 卡 (i+1) 的 K
  ...
```

**Ring Attention** 让通信与计算重叠，理论上无显存上限。

### 6.2 工程实现

- **Megatron-CP**（NVIDIA）
- **Ring Attention** (Liu et al., 2023)
- vLLM 已实验性支持 CP（多机 1M 上下文已可跑）

## 七、位置编码外推（推理侧）

> §8 详细推过 PI / NTK-aware / YaRN / LongRoPE。本节关注推理侧实战。

### 7.1 训练长度 vs 推理长度的 gap

```
训练 8K → 推理 32K：直接喂会发散
训练 8K → 推理 128K：必须用外推方案
训练 32K → 推理 128K：YaRN / LongRoPE 已工程成熟
训练 128K → 推理 1M：通常需要 longrope 或 long fine-tune
```

### 7.2 主流方案速查

| 方法 | 训练参与 | 推理改 | 备注 |
|------|----------|--------|------|
| Position Interpolation (PI) | 一般需 fine-tune | RoPE base × scale | 简单，质量一般 |
| NTK-aware | 训练免费 | RoPE base × scale^(d/(d-2)) | 中等 |
| YaRN | 通常 fine-tune | 分频率分段缩放 + 温度修正 | **2024 工业首选** |
| LongRoPE | fine-tune + 进化搜索 | 不均匀 dim-wise scale | Microsoft Phi-3 用 |

### 7.3 推理时的位置外推与 KV 驱逐的交互

KV 驱逐改了 token 位置布局 → 必须把保留 token 的 position id 重映射成连续，否则位置编码失效。StreamingLLM 等方法本身就是基于 position re-mapping 的。

## 八、KV 卸载（Offload）：HBM 之外的层次

### 8.1 三层层次

```
HBM            ─ 当前 batch 活跃 KV
DRAM           ─ 暂时不访问的 KV，prefetch 回来
SSD / NVMe     ─ 长尾、低频 KV
```

Mooncake 把这一层抽象成集群级 KV pool。单机也能做：

- **CacheGen**（2024）：KV 按重要性分层；近期 token KV → HBM，远期 → DRAM
- **DeepSpeed-FastGen / FlexLLMGen**：CPU offload KV

代价：访问 DRAM 比 HBM 慢 ~20×，SSD 慢 ~1000×；需要 prefetch + overlap。

## 九、长上下文推理"组合拳"实战配方

> 不同长度 / 任务用不同组合。

### 9.1 32K 上下文（常规长上下文）

- KV：FP8 量化
- Prefill：chunked prefill（chunk_size 2048）
- 位置：训练时已含 32K，无需外推
- 估算：单 H100 跑 70B 模型，并发 8–16 路

### 9.2 128K 上下文（RAG / 长文档）

- KV：FP8 + SnapKV（保留最重要的 16K）或 H2O
- Prefill：chunked prefill + 稀疏注意力（MInference）
- 位置：YaRN / LongRoPE
- 估算：单 H100 跑 70B 并发 1–2 路；多卡 PD 分离更优

### 9.3 1M 上下文（前沿）

- KV：FP8 + StreamingLLM-style sink token + 驱逐
- Prefill：Ring Attention / Context Parallel + 稀疏（NSA / MoBA）
- 位置：LongRoPE + long-context fine-tune
- 估算：单卡不可行；至少 8 卡 H200 / DGX

## 十、关键问答

**Q1：KV FP8 和 weight FP8 是同一件事吗？**
A：不是。weight FP8 影响**所有阶段**（prefill + decode）的 GEMM；KV FP8 只影响 **decode 阶段读取 K/V 的 attention kernel** 和**显存大小**。两者数学独立、可叠加。一般工业生产会同时开。

**Q2：H2O / SnapKV / StreamingLLM 选哪个？**
A：取决于负载。**StreamingLLM** 适合无限滚动聊天（短记忆）；**H2O** 适合通用长生成；**SnapKV** 适合长 prompt + 短 output（RAG、文档摘要 QA）。SnapKV 在 RAG-like 上 4×+ KV 压缩几乎无损，最实用。

**Q3：Chunked prefill 把 1M prompt 切成多少 chunk 合适？**
A：chunk_size 通常 2048–8192。1M / 2048 = 488 chunk，仍然是合理的 forward 数量。chunk 太小 launch overhead 大，太大与 decode 抢资源。生产里**动态调**：batch 内 decode 请求多就缩小 chunk，纯 prefill 阶段放大 chunk。

**Q4：为什么 attention sink（StreamingLLM 发现的）存在？**
A：softmax 必须总归一化到 1——当模型不想"看"任何位置时，会把无意义的 weight 倾倒到序列开头几个 token（"垃圾桶"）。这是 softmax 的数学结构副产物，所有 decoder-only LLM 都有。删了 sink token 会让所有后续 token 的 attention 分布失衡。一些新模型设计（如 Cohere）引入显式 sink token。

**Q5：YaRN 比 NTK-aware 好在哪？**
A：（1）YaRN 引入**分频率分段缩放**——低频维度（语义大尺度）插值更激进，高频维度（细节）几乎不变；（2）YaRN 还修正了 attention 的温度（scale by $\sqrt{1/0.07 \cdot \log s}$），补偿稀释效应。结果：在更长上下文下质量明显优于 NTK-aware。

**Q6：1M 上下文真的有用还是 marketing？**
A：(1) **长文档摘要 / 法律 / 医学**——真实需求；(2) **代码 repo 全局理解**——真实需求，Cursor / Claude Code 已重度使用；(3) **needle test 性能** ≠ **真实长上下文推理质量**——很多模型 needle 100% 但 RULER / multi-hop QA 仍然差。所以 1M 的 "useful长度" 通常 < 实际声称的窗口大小。

**Q7：长上下文推理为什么常用 PD 分离？**
A：长上下文 prefill 极重（$O(N^2)$ FLOPs + 大显存峰值），适合放在 compute-rich 节点；decode 阶段反而**KV 大但 FLOPs 小**，适合放在 bandwidth-rich + 大显存节点（甚至 H200 / GH200）。同节点跑两者会严重冲突——这是 §12.4 PD 分离思路的延伸。
