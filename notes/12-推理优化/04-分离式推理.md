# 12.4 分离式推理（Mooncake / DistServe / Splitwise）

[← 返回框架](../../README.md) · [📎 materials.md → §12.4](../../materials.md)

---

## 〇、本节回答什么

> Prefill 是 compute-bound、Decode 是 memory-bound，本质上是**两类不同的负载**。同节点混跑会相互拖累——长 prompt 抢了 GPU、decode TPOT 抖动；大 batch decode 又让 prefill TTFT 飙升。"分离式推理（Prefill-Decode Disaggregation, PD 分离）"把它们部署到不同集群、用 KV 传输衔接，是 2024–2025 大规模 serving 的关键架构。本节讲 Splitwise、DistServe、Mooncake 的设计差异、KV 传输路径、调度、和它对 §12.2 chunked prefill 的关系。

---

## 一、动机：prefill vs decode 的根本资源冲突

### 1.1 两类负载的 Roofline 对比

| | Prefill | Decode |
|---|---|---|
| 处理 token / forward | N（整个 prompt） | 1 |
| FLOPs / forward | $O(N \cdot P)$（compute-bound） | $O(P)$（memory-bound） |
| 主要瓶颈 | Tensor Core 算力 | HBM bandwidth |
| 喜欢的 batch | 中小（FLOPs 已饱和） | 大（摊薄 weight load） |
| 喜欢的 GPU | 算力高 | bandwidth 高 / KV 显存大 |
| 用户感知指标 | TTFT | TPOT |

### 1.2 同节点混跑的三大病

```
病 1: 长 prompt prefill 占用 GPU → 同 batch 内 decode 请求 TPOT 暴涨
病 2: 大量 decode 把 batch 撑满 → 新 prompt 排队等 prefill，TTFT 长尾
病 3: KV 显存被持续 decode 的请求占满 → prefill 抢不到 KV pool
```

chunked prefill（§12.2 五）单机层面缓解了**病 1**（把 prefill 切成 chunk 与 decode 同帧）。但当集群规模上去，**病 2/3** 仍存在，且单机调度难以达到全局最优。

### 1.3 思路：把 prefill 集群与 decode 集群拆开

```
              请求到达
                 │
        ┌────────┴────────┐
        ▼                  ▼
   Prefill Cluster   ←   KV 传输   →  Decode Cluster
   （算力高 GPU）                    （bandwidth/显存大 GPU）
   batch 中小                         batch 大
   只生成 KV+第一 token              decode 直到 EOS
```

各自只优化自己的指标，互不干扰。

## 二、Splitwise（Microsoft, 2023-11）

第一个系统性提出 PD 分离的工作。

### 2.1 关键设计

- **Prefill pool**：高算力 GPU（H100），small batch、做一次 prefill 就把 KV 传走
- **Decode pool**：高 bandwidth/大显存 GPU（A100），大 batch 持续 decode
- **混合 pool**：少量节点能两用，处理突发

### 2.2 收益

- 总成本 / token ↓ 1.4×
- 在相同 SLO 下吞吐 ↑ 1.8×
- 异构 GPU 资源（同时拥有 H100 + A100）能各尽其用

### 2.3 KV 传输

KV 通过 NVLink / InfiniBand RDMA 传输：

```
Prefill 节点:
   forward 完最后一层 → KV in HBM
Decode 节点:
   收到 KV → 写入 KV pool → 开始 decode
传输:
   GPUDirect RDMA / NVLink P2P
   传输量 = 2 × L × H_kv × d_h × T × dtype （上百 MB ~ 几 GB）
```

**关键挑战**：KV 传输延迟必须小于一次 decode forward 时间，否则 PD 分离反而拖慢首 token。

## 三、DistServe（清华 + UCSD, 2024-01）

### 3.1 创新点

1. **资源拆分 + SLO 分别优化**：分别按 TTFT-SLO / TPOT-SLO 调度
2. **细粒度拆分维度**：不只 prefill/decode 拆，**TP/PP 也可不同**——prefill 走小 TP（避免通信开销），decode 走大 TP（摊薄 weight）
3. **完整的代价模型**：根据负载/请求长度分布**自动选**单体 vs 分离配置

### 3.2 工程量化

| | 单体 vLLM | DistServe |
|---|---|---|
| Goodput (满足 SLO 的请求/s) | 1× | 1.5–7× |
| TTFT P99 | 高 | 显著降低 |
| TPOT P99 | 高 | 稳定 |

> DistServe 论文给出了 PD 分离收益的理论上界与实测，是后续工作的 reference。

## 四、Mooncake（Moonshot, 2024-06）

> 把 PD 分离从"两节点"扩展到 **"KV-centric"的全集群架构**，并加入大规模 KV cache 复用。

### 4.1 三层架构

```
┌──────────────────────────────────────────────────┐
│  Conductor （全局调度器）                          │
│  - 决定新请求落到哪个 prefill node                  │
│  - 决定 prefill 完成后 KV 送到哪个 decode node      │
│  - 监控 SLO、prefix cache 命中、负载              │
└──────────────────────────────────────────────────┘
        │              │              │
┌──────────────┐ ┌──────────────┐ ┌──────────────┐
│ Prefill Pool │ │  KVCache Pool │ │ Decode Pool  │
│              │ │  (DRAM+SSD+   │ │              │
│              │ │   HBM 三层)   │ │              │
└──────────────┘ └──────────────┘ └──────────────┘
       ↕  RDMA           ↕               ↕
```

### 4.2 三大创新

#### 4.2.1 全局 KV cache pool（DRAM + SSD + 远程 HBM 三级）

| 层级 | 容量 | 延迟 | 用途 |
|------|------|------|------|
| 本地 HBM | 数十 GB | μs | 当前 batch |
| 本地 DRAM | TB 级 | ms | 热门 prefix / 暂存 |
| 集群 SSD | 数十 TB | 10ms | 长尾 prefix（多用户 system prompt） |

→ 命中率从单机的 20–30% 推到集群 80%+。

#### 4.2.2 KV 传输的拓扑感知

prefill 完成后选**离 decode 节点 RDMA 距离最近**的路径转移 KV，避免跨机架瓶颈。

#### 4.2.3 SLO-aware admission control

接入新请求前先估它会不会让现有请求违反 SLO；不行就**拒绝或排队**，比"接进来再 preempt"更稳定。

### 4.3 Mooncake 的工业意义

Kimi (Moonshot) 的线上服务用 Mooncake 架构。论文公开了**长文档 / 多轮**为主的真实负载下，PD 分离 + 全局 KV pool 的吞吐 1.5–5× 提升、TTFT 长尾大幅下降。

## 五、KV 传输的工程要点

### 5.1 KV 大小估算

```
单 sequence KV =  2 × L × H_kv × d_h × T × bytes
                  ↑                          ↑
                K+V                       token 数
```

例：Llama-3-70B（L=80, H_kv=8, d_h=128），FP16：
- prompt 4K：80 × 8 × 128 × 4096 × 2 × 2 ≈ **1.3 GB**
- prompt 32K：10.5 GB

→ 32K 长 prompt 的 KV 传输是非trivial 的：100 Gbps RDMA ≈ 12.5 GB/s → 0.8s 即纯传输延迟。

### 5.2 重叠优化

- **layer-wise 流式传输**：prefill 完一层就传一层，不等整个 prompt prefill 完
- **KV 量化叠加**：传输前压 FP8/INT4，降一半流量
- **拓扑感知调度**：同机架内优先

### 5.3 失败处理

KV 在传输中节点崩了：直接 fallback 到 decode 端 recompute prefill（贵但正确）。

## 六、单机 chunked prefill vs PD 分离：何时切换

| 规模 | 推荐 |
|------|------|
| 单机 1–8 卡 | **chunked prefill** 即可 |
| 多机几十卡 | 看负载分布；同质短请求仍可单机 |
| 大集群 + 长尾 + 多租户 | **PD 分离 + 全局 KV pool** 必备 |

判断标准：
- 平均 prompt 长度 > 4K？→ PD 分离收益开始显著
- 多租户共享 prefix 多？→ Mooncake 风格全局 KV pool 必要
- TTFT P99 SLO 严苛？→ PD 分离

## 七、PD 分离与其他技术的叠加

```
PD 分离
   ├── chunked prefill        ← 仍可在 prefill 内部做 chunk
   ├── PagedAttention         ← KV 表示，PD 分离是其上层架构
   ├── Prefix cache / Radix   ← 全局 KV pool 把它扩到集群
   ├── 推测解码（§12.3）       ← 只在 decode pool 开
   ├── 量化（§12.1）           ← weight + KV 都可量化降传输
   └── MoE（§9）               ← EP 与 PD 分离正交
```

特别注意：**EP（Expert Parallel）的 all-to-all 通信** 和 PD 分离的 KV 传输共享网络带宽——大规模 MoE 模型上线时需统一拓扑设计（DeepSeek-V3 推理用 prefill 32 卡 EP + decode 144 卡 EP 的 PD 异构方案）。

## 八、关键问答

**Q1：PD 分离与 chunked prefill 是替代关系吗？**
A：不是，是**不同层级的解法**，且常叠加。chunked prefill 在同一节点把 prefill 切碎与 decode 交错调度，解决病 1；PD 分离把它们部署到不同集群，解决病 1+2+3。生产里通常**单机走 chunked prefill，集群走 PD 分离**，prefill 节点内部仍可 chunked。

**Q2：KV 从 prefill 节点传到 decode 节点要多久？会不会成为新瓶颈？**
A：会，对长 prompt（32K+）传输延迟可达 0.5–1s，比 prefill 本身还接近。三个对策：（1）**layer-wise 流式传输**，prefill 完一层就传一层，与剩余 prefill 重叠；（2）**KV 量化**到 FP8/INT4 降一半流量；（3）**拓扑感知调度**，优先同机架内的 prefill↔decode 配对。

**Q3：什么时候 PD 分离反而不划算？**
A：（1）平均 prompt 短（< 1K）+ 输出长——decode 占绝对主导，prefill/decode 资源冲突不明显；（2）单机 8 卡以下规模——KV 传输 overhead 占比相对大；（3）模型小（< 7B）——单机吞吐够用。这些场景用 chunked prefill 即可。

**Q4：Mooncake 的"KV-centric"是什么意思？**
A：以前调度器以 GPU/batch 为中心，KV 是副产物；Mooncake 反过来：**把 KV cache 当成一等公民资源**，全集群有一个三层（HBM+DRAM+SSD）的 KV cache pool，调度器优先按"命中哪个 KV"决定请求落点。命中率高时省下整个 prefill。

**Q5：DistServe 提到的"TP 也分别选"是什么意思？**
A：prefill 是 compute-bound，大 TP（如 TP=8）反而被通信拖累；decode 是 memory-bound，大 TP 摊薄 weight load 收益高。DistServe 允许**prefill pool 用小 TP（如 2）、decode pool 用大 TP（如 8）**——同一模型在两 pool 跑不同并行配置。

**Q6：PD 分离影响 prefix cache 命中吗？**
A：影响。单机 prefix cache 在 prefill 节点天然存在；跨节点共享需要**全局 prefix index**（Mooncake 的 KV pool）。若没有全局 index，请求被调度到不同 prefill 节点会丢失命中。Mooncake 把这一层抽象为**全局 KV cache pool**，调度时按命中优先匹配 prefill 节点。

**Q7：DeepSeek-V3 / V4 这种大 MoE 推理为什么也用 PD 分离？**
A：MoE 的 EP（Expert Parallel）需要 all-to-all 通信，prefill 阶段大量并行 token 同时路由 → 通信压力极大；decode 阶段单 token 路由 → 通信少但 weight load 占主导。两阶段最优 EP 度数不同——PD 分离让 prefill 用小 EP、decode 用大 EP（DeepSeek 公布的部署是 prefill 32 卡 EP / decode 144 卡 EP），各自达到吞吐峰值。
