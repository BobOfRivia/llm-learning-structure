# 12.4 分离式推理（Splitwise / DistServe / Mooncake）

[← 返回框架](../../README.md) · [📎 materials.md → §12.4](../../materials.md)

---

## 〇、本节回答什么

> Prefill 是 **compute-bound**，decode 是 **memory-bound**，本质上是两类资源画像完全不同的负载。把它们塞在同一个 GPU 上一起跑，会相互拖累：长 prompt 抢算力 → decode TPOT 抖动；大 batch decode 把 batch slot 撑满 → 新请求 TTFT 长尾。
>
> **Prefill-Decode Disaggregation（PD 分离）** 把两个阶段部署到独立 GPU 池，再用 RDMA 把 KV cache 从 prefill 节点传到 decode 节点。这是 2024–2025 大规模 LLM serving 的事实标准架构。本节系统讲清三篇代表作 —— Microsoft **Splitwise**、清华+UCSD **DistServe**、Moonshot **Mooncake** —— 的差异、KV 传输的工程要点、以及它与单机优化（chunked prefill、prefix cache）的层次关系。

---

## 一、动机：为什么 prefill / decode 要拆开

### 1.1 两类负载的 Roofline 画像

| 维度 | Prefill | Decode |
|---|---|---|
| 每次 forward 处理 token 数 | $N$（整个 prompt） | $1$ |
| FLOPs / forward | $O(N \cdot P)$ | $O(P)$ |
| HBM 读取量 | weight + KV写 + activation | weight + KV读（≈ weight 数量级） |
| 主瓶颈 | Tensor Core 算力 | HBM 带宽 |
| 喜欢的 batch | 小到中（FLOPs 已饱和） | 越大越好（摊薄 weight load） |
| 用户感知 SLO | TTFT（首 token 延迟） | TPOT / ITL（token 间延迟） |
| 适配硬件 | 算力高（H100/H200） | 带宽高、显存大（A100/H800） |

Splitwise 论文给的一个直观数据点：**BLOOM-176B 上，1500 token 的 prompt prefill 时间 ≈ decode 出 6 个 token 的时间** —— 一次长 prompt 就够把 batch 内所有 decode 请求的 TPOT 拉爆。([Splitwise blog](https://www.microsoft.com/en-us/research/blog/splitwise-improves-gpu-usage-by-splitting-llm-inference-phases/))

### 1.2 同节点混跑的三个症状

```
症状 1（prefill 干扰 decode）
   长 prompt 进入 → 同 batch 内所有 decode 请求 TPOT 暴涨
   用户体感：流式输出忽快忽慢

症状 2（decode 阻塞 prefill）
   大量 decode 把 continuous batch 撑满
   新 prompt 只能排队等空 slot → TTFT P99 长尾

症状 3（KV pool 资源竞争）
   长 decode 请求长期占住 KV 显存
   新 prompt 的 KV 装不下 → 触发 preemption / swap
```

### 1.3 单机的 chunked prefill 缓解了什么

Sarathi-Serve（§12.2）的 **chunked prefill** 把长 prompt 切成多个 chunk，每个 chunk 与若干 decode 请求拼成一个混合 batch 同时跑。这从单机调度层面把症状 1 转化为可控的"chunk 大小 vs decode 抖动"权衡。

但是它不能解决：
- **症状 2、3**：单机层面无论怎么调度，prefill 和 decode **争夺同一份 GPU 算力/显存预算**；
- **硬件适配错配**：同一种 GPU 既不擅长 prefill 也不擅长 decode；
- **并行策略冲突**：prefill 适合小 TP（通信少），decode 适合大 TP（摊薄 weight），单机里只能选一个。

### 1.4 PD 分离的根本思路

```
                    请求到达
                       │
              ┌────────┴────────┐
              ▼                  ▼
        Prefill 集群    ──KV传输──>   Decode 集群
        （算力优先）                  （带宽/显存优先）
        小 batch、小 TP              大 batch、大 TP
        产出：KV + 首 token          消费：KV，直到 EOS
```

两个集群各自按自己的 SLO 优化、互不抢资源。这就是 PD 分离的核心。

## 二、Splitwise（Microsoft Research, 2023-11）

第一篇系统性论证 PD 分离的论文，发表于 ISCA 2024。([arXiv:2311.18677](https://arxiv.org/abs/2311.18677))

### 2.1 核心观察

Splitwise 在 production trace 上量化了 prefill / decode 的资源画像差异，结论是：
- Prefill 是**算力受限**，HBM 带宽利用率低；
- Decode 是**带宽受限**，算力利用率低；
- 因此**在同一个 H100 上跑两者就同时浪费**两边资源。

### 2.2 关键设计

1. **Prefill pool**：高算力 GPU（H100），小到中 batch；
2. **Decode pool**：高带宽 / 大显存 GPU（A100），大 batch 持续 decode；
3. **混合 pool**：少量节点保留同节点 prefill+decode 能力，处理突发或异常请求；
4. **Layer-wise KV 传输**（§2.4 详述）。

### 2.3 实测收益（vs. Baseline-H100）

来自论文 Abstract 的两个核心数字（**严格按原文**）：

| 配置 | 吞吐 | 成本 | 功耗 |
|---|---|---|---|
| 同吞吐预算 | 1.0× | **-20%** | 持平 |
| 同成本/同功耗预算 | **2.35×** | 持平 | 持平 |

> 注：网络上流传的 "1.4× 吞吐" 对应"**降 20% 成本**前提下仍能多出 1.4× 吞吐"这一组合点位，不是独立指标。可参考 Microsoft 官方博客的总结。([Microsoft Research blog](https://www.microsoft.com/en-us/research/blog/splitwise-improves-gpu-usage-by-splitting-llm-inference-phases/))

### 2.4 Splitwise 提出的关键工程技巧：Layer-wise KV 传输

KV 传输有两种路径：

| 方式 | 行为 | 缺点 |
|---|---|---|
| **By-request** | 整个 prefill 跑完再一次性把 KV 发出去 | 串行，TTST（time-to-second-token）= prefill 时间 + 全部 KV 传输时间 |
| **By-layer**（Splitwise） | 每跑完一层就**异步**把这一层 KV 发出去 | 通信与剩余层的计算**重叠**，只剩最后一层 KV 不能藏 |

收益：**TTST ≈ prefill 时间 + 最后一层 KV 传输时间**（其它层完全被算计算 mask 掉）。这是后续所有 PD 分离系统（DistServe / Mooncake / Dynamo）的标配。

## 三、DistServe（清华 PKU + UCSD, OSDI 2024）

([arXiv:2401.09670](https://arxiv.org/abs/2401.09670))，论文最大贡献是把 PD 分离从"两个节点"上升为**"按 SLO 联合求解最优拓扑+并行策略"**。

### 3.1 三个关键创新

1. **Goodput 指标**：不是裸吞吐，而是 **"满足 TTFT-SLO 和 TPOT-SLO 的请求/秒"**，更贴近线上真实价值。
2. **按阶段独立选并行度**：
   - Prefill 走小 TP（避免 NVLink/all-reduce 开销），
   - Decode 走大 TP（摊薄 weight load），
   - 同一模型在两个 pool 里**跑不同的并行配置**。
3. **拓扑感知的 placement**：
   - 跨节点 RDMA 带宽有限时，倾向把成对的 prefill ↔ decode **绑在同一节点内**，利用 NVLink（A100 600 GB/s）做 KV 传输；
   - 跨节点带宽充足时再展开成真正的"两集群"。

### 3.2 实测收益（vs. SOTA 单体系统 vLLM）

论文 Abstract 原文：

> *"DistServe can serve **7.4× more requests** or **12.6× tighter SLO**, compared to state-of-the-art systems, while staying within latency constraints for > 90% of requests."*

— [USENIX OSDI'24 paper](https://www.usenix.org/conference/osdi24/presentation/zhong-yinmin)

注意这两个数字是 **"或"** 关系：要么同 SLO 下吞 7.4×，要么同吞吐下把 SLO 收紧到 1/12.6。不要错引为 "7.4× 吞吐 + 12.6× SLO 同时"。

### 3.3 KV 传输 overhead 实例（论文给出的具体数据）

OPT-66B、512-token 请求、10 rps：

```
单请求 KV ≈ 1.13 GB
所需链路带宽 = 1.13 GB × 10 / s ≈ 90 Gbps
```

这恰好接近一根 100 Gbps RDMA 网卡的极限——所以 placement 必须考虑实际链路。

## 四、Mooncake（Moonshot AI, 2024-06；FAST 2025）

([arXiv:2407.00079](https://arxiv.org/abs/2407.00079))，把 PD 分离从"两层架构"扩展为**以 KVCache 为中心的全集群架构**。

### 4.1 三层架构

```
┌────────────────────────────────────────────────────┐
│  Conductor （全局调度器，KVCache-centric）           │
│  - 收到请求 → 查全局 KV index → 匹配命中最高的 prefill 节点 │
│  - prefill 完成 → 调度 KV 转到合适的 decode 节点      │
│  - 持续监控 SLO、prefill/decode pool 负载             │
└────────────────────────────────────────────────────┘
        │              │              │
        ▼              ▼              ▼
┌──────────────┐ ┌──────────────────────┐ ┌──────────────┐
│ Prefill Pool │ │ 分布式 KVCache Pool    │ │ Decode Pool  │
│              │ │ HBM > DRAM > SSD       │ │              │
│              │ │ （Messenger / RDMA）   │ │              │
└──────────────┘ └──────────────────────┘ └──────────────┘
```

### 4.2 三个关键设计

#### 4.2.1 分级 KVCache pool（HBM > DRAM > SSD）

Mooncake **利用集群里被闲置的 CPU、DRAM、SSD 和 NIC** 拼成一个跨机的 KV cache pool。论文里明确的层级关系是 **HBM > DRAM > SSD**，并维持一条强一致性规则：

> *"if data resides in HBM, it must also be present in DRAM"* — 论文 §3 KVCache Pool

| 层级 | 位置 | 容量量级 | 用途 |
|---|---|---|---|
| HBM | GPU 卡内 | 80 GB / 卡（A800） | 当前在跑的请求 |
| DRAM | host 端 / 跨机 RDMA 可读 | TB 级 / 节点 | 热门 prefix、刚 evict 的请求 |
| SSD | 集群级 | 数十 TB | 长尾 prefix（如多用户共用 system prompt） |

KV block 以 **page 形式**存储，淘汰策略支持 LRU / LFU 等。命中率从单机的 ~20-30% 推到集群 80%+（论文 §4 评估）。

#### 4.2.2 Messenger：RDMA 跨机 KV 传输

Mooncake 实现了一个名为 **Messenger** 的高速 KV 搬运服务（基于 RDMA）。配合 Splitwise 提出的 layer-wise streaming，KV 传输时间被基本藏进 prefill 计算里。

> 严谨提示：论文**没有展开拓扑感知的具体路径选择算法**（早期版本博客和二手解读中常说的"拓扑感知调度"是工程实现描述，不是论文核心 contribution）。

#### 4.2.3 基于预测的早期拒绝（Early Rejection based on Prediction）

过载时，**在 prefill 之前**就预测：

1. 这个请求若进入 decode pool，预计 TPOT 是否会超 SLO？
2. 当前 decode pool 的平均 TBT（time-between-tokens）比已经超阈了吗？

若任一预测命中，**直接拒绝**这个请求（不进入 prefill）——避免"先 prefill 半天再发现 decode 装不下" 的浪费。

> 论文里有一个细节：朴素的"看当下负载就拒绝"会引发 prefill / decode pool **反相振荡**（一个忙时另一个闲）；基于预测的拒绝才能稳定下来。

### 4.3 公开的性能数据（严格按论文）

| 场景 | 提升 vs vLLM 基线 |
|---|---|
| **长上下文模拟负载** | 最高 **525% 吞吐**（即 ~5.25×） |
| **真实 trace 重放（23,000 请求）** | **+75% 请求容量**，同时满足 SLO |
| **ArXiv / L-Eval 公开数据集** | +20–40% 吞吐 |
| **早期拒绝优化** | 拒绝请求数 4183 → 3589 |

Mooncake 是 **Kimi 线上服务的主用 serving 平台**（论文明确表述："*the primary platform for serving Kimi*"）。

## 五、KV 传输的工程要点

### 5.1 单请求 KV 大小估算

$$
\text{KV}_{\text{seq}} = 2 \cdot L \cdot H_{kv} \cdot d_h \cdot T \cdot \text{bytes}
$$

其中 $2$ 是 K+V，$L$ 层数，$H_{kv}$ KV head 数（GQA），$d_h$ head 维度，$T$ token 数。

**Llama-3-70B**（$L=80$, $H_{kv}=8$, $d_h=128$, FP16）：

| Prompt 长度 | KV 大小 | 100 Gbps RDMA 纯传输延迟 |
|---|---|---|
| 4 K | $\approx$ 1.31 GB | $\approx$ 105 ms |
| 32 K | $\approx$ 10.5 GB | $\approx$ 840 ms |
| 128 K | $\approx$ 42 GB | $\approx$ 3.4 s |

→ **32K 以上 prompt 的 KV 传输绝对不能等 prefill 整段做完再发**，必须 layer-wise 重叠。

### 5.2 三种降低 KV 传输延迟的手段

| 手段 | 来源 | 效果 |
|---|---|---|
| **Layer-wise streaming**（异步逐层发） | Splitwise → 所有后继系统 | 把传输时间藏进 prefill 计算 |
| **KV 量化（FP8 / INT4）** | KV cache 量化文献 | 流量减半到 1/4 |
| **拓扑就近 placement** | DistServe | 尽量让 prefill ↔ decode 在同节点 / 同机架 |

### 5.3 失败处理

KV 在传输途中节点宕机：直接**让 decode 端 recompute prefill**（贵但语义正确，是 vLLM disaggregated serving 的当前 fallback 策略）。

## 六、何时用单机 chunked prefill、何时上 PD 分离

| 规模 / 场景 | 推荐 |
|---|---|
| 单机 1–8 卡，prompt 中短 | **chunked prefill** 即可 |
| 多机几十卡，同质短请求 | chunked prefill + 简单负载均衡 |
| 多机几十卡，长 prompt + 长尾 | **PD 分离**起步 |
| 大集群 + 多租户 + 共享 prefix | **PD 分离 + 全局 KVCache pool**（Mooncake 风格） |

经验阈值：
- 平均 prompt > 4K：PD 分离收益开始显著；
- 多租户共享 system prompt：必须有全局 KV index 才能拿到 prefix 命中红利；
- TTFT P99 SLO 严苛（< 1 s 量级）：PD 分离避免长 prompt 拖累。

## 七、PD 分离与其他技术的叠加关系

```
PD 分离（架构层）
   ├── chunked prefill        ← prefill pool 内部仍可 chunk
   ├── PagedAttention         ← KV 表示层，PD 在它之上
   ├── Prefix cache / Radix   ← Mooncake 把它升级为集群级 KVCache pool
   ├── 推测解码（§12.3）       ← 只在 decode pool 开
   ├── 量化（§12.1）           ← weight + KV 都可量化降传输
   └── MoE / EP（§9）          ← 与 PD 分离正交，但要联合优化
```

### DeepSeek-V3 的真实部署配置（按官方 Technical Report §6.4）

| 阶段 | GPU 数 | 节点 | 并行策略 |
|---|---|---|---|
| Prefill | **32** | 4 节点 × 8 卡 | **TP4 + SP + DP8 + EP32**（MoE 部分 EP32，每卡 8 + 1 冗余 expert） |
| Decode | **144** | 18 节点 × 8 卡 | **DP144 + EP144** |

源自 [DeepSeek-V3 Technical Report §6.4](https://arxiv.org/abs/2412.19437)，[LMSYS 也做过 96 H100 上的等价复现](https://www.lmsys.org/blog/2025-05-05-large-scale-ep/)。

注意要点：
- 两阶段 EP 度数不同（32 vs 144），是因为 prefill 大 EP 反而被 all-to-all 通信吃掉，decode 阶段 weight load 占主导才需要大 EP 摊薄；
- Prefill 跑**两个 micro-batch 重叠**：一个 batch 的 attention/MoE 计算与另一个 batch 的 dispatch/combine 通信 overlap；
- KV 传输用 NVIDIA 的 NIXL 库（GTC 2025 开源）。

## 八、关键问答

**Q1：PD 分离与 chunked prefill 是替代关系吗？**
A：不是。**层次不同**且常叠加：chunked prefill 在**单节点**内把 prefill 切碎与 decode 交错，解决症状 1；PD 分离把两阶段拆到**不同集群**，解决症状 1+2+3。线上典型配置是：集群层做 PD 分离，prefill pool 内部仍开 chunked prefill。

**Q2：KV 传输会不会成为新瓶颈？**
A：会，长 prompt（32K+）的 KV 可达 10+ GB，100 Gbps RDMA 纯传输就是数百毫秒。三个对策：
1. **Layer-wise streaming**（Splitwise 首创）—— 边算边发，TTST = prefill + 最后一层 KV 传输；
2. **KV 量化** 到 FP8 / INT4 —— 流量减半到 1/4；
3. **同节点 / 同机架优先 placement**（DistServe 的拓扑感知）。

**Q3：什么时候 PD 分离不划算？**
A：
- 平均 prompt 短（< 1K）+ 输出长 —— decode 占主导，prefill 资源冲突不明显；
- 规模 ≤ 单节点 8 卡 —— KV 传输 overhead 占比相对大；
- 模型小（< 7B）—— 单机吞吐够用。
这些场景 chunked prefill 即可。

**Q4：Mooncake 的"KVCache-centric"到底是什么意思？**
A：传统调度器把 GPU/batch 当一等公民、KV 是副产物；Mooncake 反过来，**把 KVCache 当成一等公民资源**：
1. 全集群一个分级 KV cache pool（HBM > DRAM > SSD）；
2. 调度新请求时**先查全局 KV index**，按"哪个 prefill 节点能命中最多 prefix"决定落点；
3. 命中越多，越省 prefill 算力。

**Q5：DistServe 说"prefill / decode 用不同 TP"，怎么理解？**
A：
- Prefill 是 compute-bound，**大 TP 反被 all-reduce 通信拖累**，所以 prefill pool 用小 TP（如 TP=2 或 4）；
- Decode 是 memory-bound，**大 TP 能摊薄每次的 weight load**（每卡只加载 1/TP 的权重），所以 decode pool 用大 TP（如 TP=8）；
- 同一模型在两个 pool 里跑不同的 shard 划分——这是单机系统做不到的。

**Q6：PD 分离会不会让 prefix cache 命中率下降？**
A：会，**如果没有全局 KV index**。单机时 prefix cache 天然就在本机，prefill 节点之间不共享。Mooncake 的解法是把 prefix cache 升级为**全局 KVCache pool**，调度时按命中匹配 prefill 节点。没有全局 index 的简单 PD 分离会牺牲 prefix 命中。

**Q7：DeepSeek-V3 这种大 MoE 为什么也用 PD 分离？**
A：MoE 的 expert parallel 在两个阶段最优配置不一样：
- Prefill 阶段大量 token 并行路由 → **all-to-all 通信压力极大**，EP 不能太大，否则通信成主瓶颈；
- Decode 阶段单 token 路由 → 通信少，但 **weight load 占主导**，EP 越大每卡 weight 越少。
所以 prefill 用 EP=32、decode 用 EP=144，各自达到吞吐峰值。这是**PD 分离 + MoE 联合优化**的典型案例。

**Q8：vLLM / SGLang / TRT-LLM 现在的 PD 分离能直接上线吗？**
A：截至 2025 年中：
- **vLLM**：PD 分离仍标为 **experimental**，但底层 KV 搬运组件 `NixlConnector`（基于 NVIDIA NIXL）已经稳定，可作生产 PoC；
- **NVIDIA Dynamo**（[ai-dynamo/dynamo](https://github.com/ai-dynamo/dynamo)）：GTC 2025 发布的官方编排层，支持 TRT-LLM / vLLM / SGLang 作为后端，PD 分离是核心特性之一；
- **Mooncake**：开源 transfer engine + KVCache pool（[kvcache-ai/Mooncake](https://github.com/kvcache-ai/Mooncake)），已被 SGLang HiCache 集成；
- **生产稳定路径**：Mooncake + SGLang，或 DeepSeek 自家 stack；
- **新项目 PoC 路径**：vLLM + NixlConnector，或直接上 Dynamo。
