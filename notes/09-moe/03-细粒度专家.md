# 9.3 架构变体：细粒度专家 + 共享专家 + Dropless

[← 返回框架](../../README.md) · [📎 materials.md → §9.3](../../materials.md)

---

## 〇、本节回答什么

§9.1 是 router 视角、§9.2 是 loss 视角。本节是 **expert 自身结构** 视角：

> 把 expert 数量、大小、分工结构改一下，能否让同算力下质量更高、负载更均衡？

三条主线：
1. **细粒度专家**（Fine-grained Experts）：N 变大，每个 expert 变小
2. **共享专家**（Shared Experts）：所有 token 都过的"公共 expert"
3. **Dropless / MegaBlocks**：从 kernel 层面消除 token drop

这三条加一起就是 **DeepSeek-MoE / V2 / V3 路线**，也是 2024-2025 主流路径。

---

## 一、细粒度专家（Fine-grained Experts）

### 1.1 直觉

```
经典 MoE (Mixtral 风格):    8 experts, top-2
DeepSeek-MoE 风格:          256 experts (其中 1 个共享 + 255 个 routed), top-8
```

总参数量、总激活量近似相同，但：
- 每个 expert 更小（hidden 减 N 倍）
- 路由分辨率更高（top-K 的 K 大，组合数 $\binom{N}{K}$ 暴增）

### 1.2 数学：组合数爆炸

- Mixtral：$\binom{8}{2} = 28$ 种 expert 组合
- DeepSeek-MoE：$\binom{63}{6} = 67,945$ 种（DS-MoE 16B 版本）
- DeepSeek-V3：$\binom{256}{8} = 4 \times 10^{14}$ 种

→ 每个 token 能选到"几乎独一无二"的 expert 组合 → 表达能力远超"每个 expert 包山包海"的粗粒度方案。

### 1.3 [DeepSeek-MoE (2024-01)](https://arxiv.org/abs/2401.06066) 的两个关键论点

1. **"专家更专"**：实测 fine-grained expert 学到的 patterns 更可解释（语言、数学、代码各有专属）
2. **"路由更稳"**：每 expert 负载小，dead expert 比例反而下降

### 1.4 代价

- **路由 router 自身 FLOPs ↑**：因 N 大，$d \times N$ 线性层变大（但仍远小于 expert）
- **All-to-All 通信压力 ↑**：每 token 要发到 top-8 个 expert（vs top-2）→ 详见 §9.4
- **工程实现**：要写更高效的 grouped-GEMM kernel

→ 但只要通信跟得上，质量优势显著。

---

## 二、共享专家（Shared Experts）

### 2.1 思路

> 不是所有知识都该是 "稀疏激活的"。**通用语言能力**（语法、常识）每个 token 都需要 —— 这部分不该走 router。

```
DeepSeek-MoE block 结构：

    token x
       │
       ├──────→ Shared Expert (每 token 都过) ──┐
       │                                          │
       └──→ Router → Top-K routed experts ──→ Σ ─→ out
                       (稀疏激活)
```

通常 1-2 个 shared expert + 256 个 routed expert。

### 2.2 解决什么问题

旧 MoE 痛点：**每个 routed expert 都在重复学习"通用语言能力"**。
→ 浪费参数容量 + 加剧路由冲突。

shared expert 把这部分单独承担 → routed experts 可以专注**长尾 / 专业知识**。

### 2.3 实测收益

DeepSeek-MoE 论文 ablation：
- 同算力下，加 shared expert → 质量提升 ~2-3% PPL
- routed expert 之间的相关性显著下降（更"专")

### 2.4 共享专家的 K

- DeepSeek-V2：1 个 shared
- DeepSeek-V3：1 个 shared expert + 256 routed（top-8）

注意：shared expert 不算入 top-K（它是必走的）。每 token 总激活 = K + n_shared。

## 三、Dropless MoE（MegaBlocks 路线）

### 3.1 为什么要 dropless

§9.2 提到 capacity_factor + token dropping 是兜底。但 drop token 直接伤质量：

```
丢一个 token = 它在该层只走 residual，没经过任何 FFN
       ─→ 信息丢失 + 训练信号削弱
```

实测 capacity=1.0 时 drop 率可达 10-30%，质量明显掉。

### 3.2 MegaBlocks 的核心 trick

[Gale et al. 2023 — MegaBlocks](https://arxiv.org/abs/2211.15841)：

> 把 "**每 expert 等大小 batch**" 的硬限制去掉，让 expert 处理变长输入。

实现：用 **block-sparse GEMM**：

```
传统 MoE batched GEMM（要求 expert 输入等大小）:
  input shape: [N, C, d]   ← N expert, C capacity, d hidden

MegaBlocks (block-sparse):
  把所有 token 拼成一个长序列 [T, d]，
  按 expert index 排序后切成 N 个变长 block，
  用 block-sparse matmul 一次性算完。
```

→ 不需要 capacity 限制、不需要 drop。

### 3.3 工程影响

- 需要专门 kernel（Block-Sparse-GEMM，cuSPARSE / triton 实现）
- DeepSpeed-MoE、Megatron-MoE 默认支持
- vLLM / SGLang 推理引擎也已集成

### 3.4 副作用

- block-sparse GEMM 比 dense GEMM 慢 ~10-20%（kernel 优化空间）
- 显存峰值仍要按 worst case 算
- 但**质量提升通常 > 速度损失**，工业上普遍采纳

→ 当下"现代 MoE"基本上就是 **细粒度 + 共享 + dropless** 三件套。

## 四、其他架构变体（不深入）

### 4.1 Layer-wise Mixture（粗粒度层间 MoE）

[Mod-Squad](https://arxiv.org/abs/2212.08066) / [Branch-Train-Merge](https://arxiv.org/abs/2208.03306)：

> 不是每个 token 选 expert，而是 **整段任务** 选一个 model（expert = 完整模型）。

- 优点：训练简单（每个 expert 独立训）
- 缺点：粒度太粗，质量不如 token-level MoE
- 用作 baseline，工业少用

### 4.2 Hash + Hierarchical Routing

[V-MoE](https://arxiv.org/abs/2106.05974) / [Hierarchical Routing](https://arxiv.org/abs/2305.14705)：

> 先用粗 router 分组（hash），再用细 router 选 expert，类似 "B+ 树"。

- 适合 N 很大（1k+）时的路由分摊
- DeepSeek-V3 没用，但是未来 expert 数继续涨可能成为标配

### 4.3 MoA（Mixture of Attention）

[Zhang et al. 2022 — MoA](https://arxiv.org/abs/2210.05144)：

> 把 attention head 也做成 MoE（不只是 FFN）。

- 实操少见，attention head 数较少，MoE 收益有限
- 工业 MoE 仍以 FFN 为主

### 4.4 Expert sub-grouping

[GLaM / Switch-C](https://arxiv.org/abs/2202.08906)：
- 把 expert 按 group 组织（相邻 expert 共用部分参数）
- 减少总参数同时保留路由分辨率
- DeepSeek-MoE 早期尝试过 group + share，最终演化成"shared expert"形态

## 五、DeepSeek-V3 全景示例

[DeepSeek-V3](https://arxiv.org/abs/2412.19437) 是这套架构的集大成：

| 维度 | 数值 |
|------|------|
| 总参数 | 671B |
| 每 token 激活参数 | 37B |
| MoE 层 expert 数 | **1 shared + 256 routed** |
| top-K | 8 routed (+ 1 shared) |
| 路由方式 | **Aux-Loss-Free**（§9.2） |
| 通信 | EP=64 + All-to-All（§9.4） |
| Dropless | 是 |

```
Block 结构（简化）：
  x ─→ LayerNorm
       ├─→ MLA (attention，见 §5.4)
       │
       ├─→ LayerNorm
       │
       └─→ MoE FFN
            ├─→ Shared Expert (每 token 必过)
            └─→ Router → Top-8 Routed Experts
                          (256 选 8, 加 bias)
```

→ DeepSeek-V3 的成功 ≈ 这套架构 + 数据 + 训练 recipe 的组合。其他家（Llama-4、Qwen3-MoE、Kimi K2）2025 年都向这个方向收敛。

## 六、关键问答

**Q1**：细粒度专家越细越好吗？
- 不是，N 太大有两个上限：
  - **router 算力**：$d \times N$ 线性层开销线性涨
  - **通信开销**：All-to-All 每 token 要发到更多目标
- 当前 sweet spot：N = 128-256，top-K = 6-8
- 再大暂时没看到质量收益

**Q2**：shared expert 数量怎么选？
- DeepSeek-V2/V3：1 个 shared
- 实验过 2-4 个 shared 收益边际递减
- 通用 token 不需要"很多"通用 expert
- 一般 1 个够

**Q3**：dropless 一定要用 MegaBlocks 吗？
- 算法上：dropless = 不丢任何 token
- 实现上：
  - MegaBlocks（block-sparse GEMM）：主流
  - **Cutlass grouped GEMM**：NVIDIA 提供的高效变长 batched GEMM，DeepSeek 用这个
  - 朴素 padding + mask：实现简单，但浪费显存
- 三种选一即可

**Q4**：细粒度 + 共享 + dropless 哪个收益最大？
- DeepSeek-MoE ablation 结论：
  - 细粒度（fine-grained）：~3% PPL ↓
  - shared expert：~2% PPL ↓
  - dropless：~2-5% PPL ↓（capacity 越紧收益越大）
- 三者**正交可叠加**，加起来约 7-10%

**Q5**：Mixtral 8x7B 为什么没采用这些 trick？
- Mixtral 2023-12 发布，时间早于 DeepSeek-MoE
- 走的是 GShard 经典路线（top-2 + aux loss + 8 expert）
- 实测：Mixtral 在质量上确实弱于同算力 DeepSeek-MoE
- → "用什么 MoE 架构"成为新一轮分水岭

**Q6**：fine-grained 专家更专，能验证吗？
- DeepSeek-MoE 论文做了可视化：
  - 部分 expert 对中文 / 数学 / 代码强 activation
  - shared expert 在所有数据上均匀 active
- 也有研究质疑 "expert specialization" 在 LLM 上不如 vision 明显
- 但工程上 fine-grained 质量数据是确定的

**Q7**：细粒度 expert 训练会不会更慢收敛？
- 不会。专家小 → 每个 expert 更新次数多 → 单 expert 收敛快
- 但总 expert 数多 → 整体训练 token 需求略升
- DeepSeek-V3 vs Mixtral：同 quality 训练 token 数差不多
