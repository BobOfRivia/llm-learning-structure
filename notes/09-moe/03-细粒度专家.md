# 9.3 架构变体：细粒度专家 + 共享专家 + Dropless

[← 返回框架](../../README.md) · [📎 materials.md → §9.3](../../materials.md)

---

## 〇、本节回答什么

§9.1 是 router 视角、§9.2 是 loss 视角。本节是 **expert 自身结构** 视角：

> 把 expert 数量、大小、分工结构改一下，能否让同算力下质量更高、负载更均衡？

三条主线：
1. **细粒度专家**（Fine-grained Experts）：N 变大，每个 expert 变小
2. **共享专家**（Shared Experts）：所有 token 都过的"公共 expert"
3. **Dropless / MegaBlocks**：从 kernel 层面消除 token drop

这三条加一起就是 **DeepSeek-MoE / V2 / V3 路线**，也是 2024-2025 主流路径。

本节我们会：
- 用 **granularity scaling law**（Krajewski et al. 2024）证明"为什么细粒度更优"
- 给出 shared expert 的**完整数学结构**（与 routed expert 的加权方式）
- 拆解 dropless 的 **block-sparse GEMM** 算法

## 一、细粒度专家（Fine-grained Experts）

### 1.1 直觉与对照

```
经典 MoE (Mixtral 风格):    8 experts, top-2,  K/N = 25%
DeepSeek-MoE 风格:          256 experts (其中 1 个共享 + 255 个 routed), top-8, K/N ≈ 3.1%
```

总参数量、总激活量近似相同，但：

- 每个 expert 更小（hidden 减 N 倍）
- 路由分辨率更高（top-K 的 K 大，组合数 $\binom{N}{K}$ 暴增）

### 1.2 数学：保持算力不变的"等容量重排"

要让"细粒度 MoE"和"粗粒度 MoE"公平对比，需要保持两个量不变：

1. **总参数量** $P_{\text{total}}$：决定显存
2. **激活参数量** $P_{\text{active}}$（单 token 算力）：决定计算成本

设 dense baseline 单 FFN 有 $P_{\text{FFN}} = 8 d^2$ 参数。粗粒度 MoE 与细粒度 MoE 都基于 8 倍的总参数：

| 配置 | $N$ | $K$ | 单 expert 参数 | $P_{\text{total}}$ | $P_{\text{active}}$ |
|---|---|---|---|---|---|
| 粗粒度（Mixtral 风格） | 8 | 2 | $P_{\text{FFN}}$ | $8 P_{\text{FFN}}$ | $2 P_{\text{FFN}}$ |
| **细粒度（DeepSeek 风格）** | 64 | 16 | $P_{\text{FFN}} / 8$ | $8 P_{\text{FFN}}$ | $2 P_{\text{FFN}}$ |

→ 总参数和激活参数都不变，但**组合数从 $\binom{8}{2} = 28$ 涨到 $\binom{64}{16} \approx 4.9 \times 10^{14}$**。

### 1.3 Granularity（粒度）的形式化定义

[Krajewski et al. 2024 — Scaling Laws for Fine-Grained MoE](https://arxiv.org/abs/2402.07871) 把"粒度"形式化为：

$$G = \frac{d_{\text{ff}}^{\text{dense}}}{d_{\text{ff}}^{\text{expert}}}$$

- $d_{\text{ff}}^{\text{dense}}$ = 同参数预算的 dense baseline FFN hidden dim
- $d_{\text{ff}}^{\text{expert}}$ = MoE 中单个 expert 的 hidden dim
- $G = 1$：每个 expert 大小 = dense FFN（粗粒度，Mixtral）
- $G > 1$：expert 比 dense FFN 小（细粒度，DeepSeek）
- $G = 8$：每 expert 小 8 倍（DeepSeek-V3 量级）

**关键关系**：$N \cdot K = G \cdot (K_{\text{baseline}} = 2)$，即"专家数 × 激活数 ≈ G 倍 baseline 激活数"——保持总算力不变。

### 1.4 组合数爆炸的物理含义

| 模型 | $N$ | $K$ | 组合数 $\binom{N}{K}$ |
|---|---|---|---|
| Switch (top-1) | 16 | 1 | 16 |
| Mixtral | 8 | 2 | 28 |
| DeepSeek-MoE 16B | 64 | 6 | 74,613 |
| DeepSeek-V2 | 160 | 6 | $2.6 \times 10^{10}$ |
| **DeepSeek-V3** | 256 | 8 | $4 \times 10^{14}$ |

→ 每个 token 能选到"几乎独一无二"的 expert 组合 → 表达能力远超"每个 expert 包山包海"的粗粒度方案。

**类比**：粗粒度 ≈ 把所有书分成 8 类（"科技、文学、历史..."），每本书只能贴 2 个标签；细粒度 ≈ 分成 256 类，每本书贴 8 个标签 → 描述精度暴增。

### 1.5 Granularity Scaling Law（核心结果）

Krajewski et al. 2024 用大量实验拟合出：

$$L(N_{\text{total}}, N_{\text{active}}, D, G) = c + \frac{a}{N_{\text{total}}^{\alpha}} + \frac{b}{N_{\text{active}}^{\beta}} + \frac{e}{D^{\delta}} + \frac{h}{G^{\gamma}}$$

- $L$：验证 loss
- $N_{\text{total}}$：总参数
- $N_{\text{active}}$：激活参数（单 token）
- $D$：训练 token 数
- $G$：granularity
- $a, b, c, e, h, \alpha, \beta, \delta, \gamma$：拟合系数

**关键发现**（论文 §5）：

1. **G 是单独的 scaling 维度**：在固定 $N_{\text{total}}, N_{\text{active}}, D$ 下，loss 随 $G$ 增大持续下降（直到 G ≈ 16 才有边际效应递减）
2. **最优 G 与算力预算耦合**：算力越大，最优 G 越大（Krajewski et al. 的拟合给出 $G_{\text{opt}} \propto C^{0.2}$ 左右）
3. **G = 8-16 是 sweet spot**：这是 DeepSeek-V3 选 256 expert 的理论依据

**实测对比**（论文表 1，固定 $N_{\text{active}} = $ baseline）：

| G | val loss | 相对 dense（G=0）改进 |
|---|---|---|
| 1（Mixtral 风格） | 2.83 | +0.7% |
| 4 | 2.79 | +2.1% |
| 8 | 2.75 | +3.5% |
| 16 | 2.74 | +3.8% |
| 32 | 2.74 | +3.9%（饱和） |

→ G 从 1 涨到 8 收益显著，>16 后几乎饱和。

### 1.6 单 expert 维度公式

细粒度 expert 怎么算出每个 expert 的具体尺寸？

设 dense baseline：$d_{\text{model}} = 4096, d_{\text{ff}} = 4 \cdot d_{\text{model}} = 16384$，单 FFN 参数 ≈ $2 \cdot 4096 \cdot 16384 \approx 134M$。

细粒度配置（DSv3 风格，G=8）：

$$d_{\text{ff}}^{\text{expert}} = d_{\text{ff}}^{\text{dense}} / G = 16384 / 8 = 2048$$

每个 expert：$2 \cdot 4096 \cdot 2048 = 16.8M$ 参数。

256 个 expert 总计 $4.3B$ FFN 参数 vs dense 的 $134M$ —— 32× 总参数容量，但每 token 算力（top-8）= $8 \cdot 16.8M = 134M$，与 dense 一致。

**DSv3 实际配置**（论文 §2.2）：

- $d_{\text{model}} = 7168$
- 每个 routed expert $d_{\text{ff}}^{\text{expert}} \approx 2048$
- 共享 expert $d_{\text{ff}}^{\text{shared}} \approx 2048$（同样小）
- 总 routed expert 数 256 + 1 shared，top-8 routed + 1 shared

### 1.7 细粒度的代价

```
代价 = 工程复杂度 + 通信
```

1. **Router 自身 FLOPs ↑**：因 N 大，$d \times N$ 线性层变大
   - DSv3: $W_g \in \mathbb{R}^{7168 \times 256}$ = 1.8M 参数（仍远小于 expert）
   - 但 router forward 时间从 $O(d \cdot 8)$ 涨到 $O(d \cdot 256)$，~30× 时间
2. **All-to-All 通信压力 ↑**：每 token 要发到 top-8 个 expert（vs top-2）→ 详见 §9.4
   - 通信量正比于 K，从 K=2 到 K=8 是 4× 通信
3. **Grouped GEMM 实现**：要写更高效的 batched FFN kernel
4. **训练超参更敏感**：N 越大，aux loss / bias 越难调（DSv3 用 aux-loss-free 解决）

→ 只要通信跟得上（NVLink + InfiniBand），质量优势显著。

## 二、共享专家（Shared Experts）

### 2.1 思路与结构

> 不是所有知识都该是"稀疏激活的"。**通用语言能力**（语法、常识、tokenizer artifacts）每个 token 都需要 —— 这部分不该走 router。

```
DeepSeek-MoE block 结构：

    x ─→ LayerNorm ─→ MLA (attention) ─→ + ←──────────┐
                                          │           │
                                          ▼           │
                              LayerNorm                │
                                  │                    │
                       ┌──────────┴──────────┐         │
                       │                     │         │
                ┌──────▼──────┐    ┌────────▼────────┐│
                │ Shared       │   │ Router → TopK   ││
                │ Expert       │   │ Routed Experts  ││
                │ (每 token 必过)│  │ (稀疏激活)      ││
                └──────┬──────┘    └────────┬────────┘│
                       │                     │         │
                       └─────── + ───────────┘         │
                               │                       │
                               └───────────────────────┘
```

### 2.2 数学：共享 + 路由的加和方式

DeepSeek-V3 论文 §2.1.1 的完整公式：

$$y = E_{\text{shared}}(x) + \sum_{i \in \text{TopK}} w_i \cdot E_i(x)$$

注意**几个关键细节**：

1. **共享 expert 不归一化进 sum**：直接加（不乘 weight）
2. **routed experts 的 $w_i$ 之和 = 1**（softmax/sigmoid 归一化后）
3. **共享 expert 的"权重" = 1**（隐含，与 routed 的 sum=1 等价）

**为什么这样设计**：

- 共享 expert 承担"基础能力"，应当总是"全力输出"，不被 router 削弱
- routed experts 之和归一化为 1 → 总 MoE 输出 ≈ $E_{\text{shared}}(x) + \text{Mix-of-Routed}(x)$
- 输出尺度可控：约等于 2 倍 dense FFN（共享 + 加权和）

### 2.3 与早期变体的对比

|  | 没有 shared | DeepSeek 的 shared | "粗暴 shared"（直接拼 dense + MoE） |
|---|---|---|---|
| 通用能力承担方 | 每 routed expert 重复学 | 1 个 shared 集中学 | 1 个 dense FFN 集中学 |
| routed expert 之间相关性 | 高（都学通用） | 低（专攻长尾） | 低 |
| 总参数 | $N \cdot P_{\text{FFN}}$ | $(N+1) \cdot P_{\text{ff}}^{\text{small}}$ | $N \cdot P_{\text{ff}}^{\text{small}} + P_{\text{FFN}}$ |
| 实现复杂度 | 低 | 中 | 高（dense + MoE 两套 forward） |

### 2.4 实测收益

DeepSeek-MoE 论文（[arxiv 2401.06066](https://arxiv.org/abs/2401.06066) §4）ablation：

- 同算力下，加 shared expert → 验证 PPL ↓ ~2-3%
- routed expert 之间的**激活相关性**（cosine similarity of activation patterns）显著下降
- routed expert 的**可解释性提升**：可以观察到不同 expert 对中文 / 代码 / 数学的强偏好（论文图 5 的 heatmap）

### 2.5 共享专家的数量

|  | shared 数 | top-K routed |
|---|---|---|
| DeepSeek-MoE 16B | 2 | 6 |
| DeepSeek-V2 | 2 | 6 |
| DeepSeek-V3 | **1** | 8 |
| Llama-4 Maverick | 1 | 1 |
| Qwen3-MoE | 0（无 shared） | 8 |

**为什么 V3 减到 1**：

- V2 实验 2 个 shared 收益边际递减（论文 ablation）
- 1 个 shared 已经能承担通用能力
- 减少 shared 数留出更多算力给 routed expert

### 2.6 共享专家的尺寸

DSv3 中共享 expert 和 routed expert 大小一致（$d_{\text{ff}} \approx 2048$）。

**为什么不让 shared 大一些**：

- 设计哲学：shared 是"通用 expert"，不应当压倒 routed 的影响
- 算力分配：单 token 总 FFN 算力 = $E_{\text{shared}}(x) + 8 \cdot E_{\text{routed}}(x) = 9 \cdot 16.8M ≈ 151M$
  - 若 shared 大 4 倍：$67M + 8 \cdot 16.8M = 201M$，算力 +33% 但收益不明显
- 简化训练：所有 expert 同尺寸，超参一致

## 三、Dropless MoE（MegaBlocks 路线）

### 3.1 为什么要 dropless

§9.2 第五节提到 capacity_factor + token dropping 是兜底。但 drop token 直接伤质量：

```
丢一个 token = 它在该层只走 residual，没经过任何 FFN
       ─→ 信息丢失 + 训练信号削弱
```

实测：

- capacity_factor = 1.0 时 drop 率可达 10-30%（取决于负载均衡程度）
- 每丢 10% token → 验证 PPL +1-2%
- 推理时如果 drop，对长 context 任务尤其敏感（信息流断裂）

### 3.2 朴素 batched GEMM 为什么需要等大小

经典 MoE 实现：

```python
# 每个 expert 收 capacity = C 个 token
expert_inputs = torch.zeros(N, C, d)
for i in range(N):
    tokens_for_i = tokens[mask_i]  # 选中去 expert i 的 token
    if len(tokens_for_i) > C:
        tokens_for_i = tokens_for_i[:C]  # drop
    elif len(tokens_for_i) < C:
        pad with zeros
    expert_inputs[i] = tokens_for_i

# 一次 batched GEMM
expert_outputs = bmm(expert_inputs, W_experts)  # [N, C, d]
```

- 必须 padding 到 C，否则 batched GEMM 张量不规整
- 但 padding 浪费算力（zero × W），drop 浪费 token

### 3.3 MegaBlocks：Block-Sparse GEMM

[Gale et al. 2023 — MegaBlocks](https://arxiv.org/abs/2211.15841) 的核心思路：

> 把 "每 expert 等大小 batch" 的硬限制去掉，让 expert 处理变长输入。

**算法**：

```
Step 1: router 决定 token 去哪个 expert
        → 得到 token-to-expert 分配 idx[t] ∈ {0, ..., N-1}

Step 2: 按 expert id **排序** token
        → 把所有去 expert 0 的 token 排在前面，去 expert 1 的接着，...
        → 排序后的 token 张量 [T_sorted, d]

Step 3: 记录每个 expert 的边界
        → block_offsets = [0, c_0, c_0+c_1, ..., T]
        → 第 i 个 expert 处理 [block_offsets[i] : block_offsets[i+1]] 区间的 token

Step 4: Block-sparse matmul
        → 把权重张量 W = [N, d, d_ff] 看作 N 个 block
        → 每个 token block 只乘对应 expert 的 W block
        → 用 cuSPARSE / Triton 写的专用 kernel 一次 GEMM 完成
```

```
Token 排序后 + 权重 block-sparse：

  Sorted Token Tensor [T, d]:                      W tensor [N·d_ff, d]:
  ┌─────────────────────┐                          ┌───────────────────────┐
  │ tokens for expert 0  │ c_0 rows                │ W_0 (d_ff x d)         │
  ├─────────────────────┤                          ├───────────────────────┤
  │ tokens for expert 1  │ c_1 rows                │ W_1 (d_ff x d)         │
  ├─────────────────────┤        ×                 ├───────────────────────┤
  │       ...            │                          │       ...              │
  ├─────────────────────┤                          ├───────────────────────┤
  │ tokens for expert N-1│ c_{N-1} rows            │ W_{N-1} (d_ff x d)     │
  └─────────────────────┘                          └───────────────────────┘

  Block-Sparse GEMM 输出 [T, d_ff]：
  ┌─────────────────────┐
  │ tokens[0:c_0] × W_0  │  ← block 0
  ├─────────────────────┤
  │ tokens[c_0:c_0+c_1] × W_1 │  ← block 1
  ├─────────────────────┤
  │       ...            │
  └─────────────────────┘
```

→ 没有 padding、没有 drop、没有 batched GEMM 的等大小约束。

### 3.4 算法复杂度

- Sort 开销：$O(T \log T)$，但因为只有 N 个 bucket，可以用 radix sort 做到 $O(T)$
- Block-sparse GEMM：$O(\sum_i c_i \cdot d \cdot d_{\text{ff}}) = O(T \cdot d \cdot d_{\text{ff}})$
- 总开销 ≈ 等价 dense FFN 的 K/N 倍（理论 sparsity）
- 实测 block-sparse kernel 比 dense GEMM 慢 ~10-20%（kernel 优化空间）

→ "10-20% 慢" 远小于 "drop 30% token 的质量损失"，工程上完全划算。

### 3.5 Cutlass Grouped GEMM（NVIDIA 方案）

DSv3 实际用的不是 MegaBlocks，而是 NVIDIA 的 **Cutlass Grouped GEMM**：

- 把 N 个不同大小的 GEMM 一起调度
- 用 stream 并发执行
- 在 Hopper H100 上专门优化
- 性能比 MegaBlocks block-sparse 高 ~10-15%

→ 现代 MoE 的 dropless 实现有三条路：

1. **MegaBlocks** (Triton block-sparse GEMM) — 最早，开源
2. **Cutlass Grouped GEMM** (NVIDIA) — H100 最优
3. **TensorRT-LLM MoE kernel** (NVIDIA) — 闭源最快

### 3.6 工程影响

- DeepSpeed-MoE、Megatron-MoE 默认支持 MegaBlocks 风格
- vLLM / SGLang 推理引擎也已集成
- 朴素 padding + mask：实现简单，但浪费显存
- → 当下"现代 MoE"基本上就是 **细粒度 + 共享 + dropless** 三件套

## 四、其他架构变体（速览）

### 4.1 Layer-wise Mixture（粗粒度层间 MoE）

[Mod-Squad](https://arxiv.org/abs/2212.08066) / [Branch-Train-Merge](https://arxiv.org/abs/2208.03306)：

> 不是每个 token 选 expert，而是 **整段任务** 选一个 model（expert = 完整模型）。

- 优点：训练简单（每个 expert 独立训）
- 缺点：粒度太粗，质量不如 token-level MoE
- 用作 baseline，工业少用

### 4.2 Hash + Hierarchical Routing

[V-MoE](https://arxiv.org/abs/2106.05974) / [Hierarchical Routing](https://arxiv.org/abs/2305.14705)：

> 先用粗 router 分组（hash 或 cluster），再用细 router 选 expert，类似 "B+ 树"。

- 适合 N 很大（1k+）时的路由分摊
- DeepSeek-V3 的 **grouped TopK**（§9.1 §5.4）是这思路的简化版
- 未来 N 继续涨到 1k+ 可能成为标配

### 4.3 MoA（Mixture of Attention）

[Zhang et al. 2022 — MoA](https://arxiv.org/abs/2210.05144)：

> 把 attention head 也做成 MoE（不只是 FFN）。

- 实操少见，attention head 数较少（typically 32-64），MoE 收益有限
- 工业 MoE 仍以 FFN 为主

### 4.4 Multi-Head MoE (MH-MoE)

[Wu et al. 2024 — MH-MoE](https://arxiv.org/abs/2404.15045)：

把 token embedding 切成 h 个 head，每个 head 独立路由到不同 expert，最后 concat。

- 优点：单 token 可激活更多"sub-expert"，分辨率高（h × K）
- 缺点：实现复杂，工程未普及

### 4.5 Expert Sub-grouping（早期共享尝试）

[GLaM / Switch-C](https://arxiv.org/abs/2202.08906)：

- 把 expert 按 group 组织（相邻 expert 共用部分参数）
- 减少总参数同时保留路由分辨率
- DeepSeek-MoE 早期尝试过 group + share，最终演化成"shared expert"形态

## 五、DeepSeek-V3 全景示例

[DeepSeek-V3](https://arxiv.org/abs/2412.19437) 是这套架构的集大成：

### 5.1 关键参数

| 维度 | 数值 |
|------|------|
| Layer 数 | 61 |
| $d_{\text{model}}$ | 7168 |
| Attention 类型 | MLA (Multi-head Latent Attention) |
| Attention head 数 | 128 |
| FFN 类型 | MoE（第 4 层起，前 3 层 dense FFN） |
| MoE 层 expert 数 | **1 shared + 256 routed** |
| top-K | 8 routed (+ 1 shared) |
| $d_{\text{ff}}^{\text{expert}}$ | 2048 |
| 总参数 | 671B |
| 单 token 激活参数 | **37B** |
| Granularity G | ≈ 8 |
| 路由方式 | **Aux-Loss-Free**（§9.2） |
| 通信 | EP=64 + Grouped TopK + All-to-All（§9.4） |
| Dropless | 是（Cutlass Grouped GEMM） |

### 5.2 Block 结构

```
Block 结构（简化）：

  x ─→ RMSNorm
       │
       ├─→ MLA (attention，见 §5.4)
       │
       │   x ←─ + ───── residual
       │   │
       ├─→ RMSNorm
       │   │
       │   ├─→ Shared Expert (每 token 必过)
       │   │
       │   └─→ Router → Top-8 Routed Experts (sigmoid + bias + grouped TopK)
       │                  └─ 加权和
       │
       └─→ + ←── shared + routed
            │
            └──────→ x_next
```

### 5.3 与 Mixtral 8x7B 的对照

| 维度 | Mixtral 8x7B | DeepSeek-V3 |
|---|---|---|
| 总参数 | 47B | **671B (14×)** |
| 激活参数 | 13B | 37B (2.8×) |
| N (routed) | 8 | **256 (32×)** |
| K | 2 | 8 |
| 单 expert 大小 | $d_{\text{ff}}/1 \approx 14336$ | $d_{\text{ff}}/8 \approx 2048$ |
| Shared expert | 无 | **1 个** |
| Granularity G | 1 | **8** |
| 路由 | softmax + aux loss | **sigmoid + aux-loss-free** |
| 组合数 | $\binom{8}{2} = 28$ | $\binom{256}{8} \approx 4 \times 10^{14}$ |
| 实测同算力质量 | baseline | **+15-20% 各项 benchmark** |

→ DSv3 的成功 ≈ 这套架构 + 数据 + 训练 recipe 的组合。其他家（Llama-4、Qwen3-MoE、Kimi K2）2025 年都向这个方向收敛。

---

## 六、Expert Specialization 实证

细粒度 expert 的卖点是"更专"，能验证吗？

### 6.1 DeepSeek-MoE 论文的可视化

[DeepSeek-MoE](https://arxiv.org/abs/2401.06066) §4.3 做了 expert activation 热图：

- 部分 expert 对**中文** token 强 activation（汉字、CJK punctuation）
- 部分 expert 对**数学符号**强 activation（运算符、数字）
- 部分 expert 对**代码**强 activation（关键字、括号）
- **shared expert 在所有数据上均匀 activation**（符合"通用能力"定位）

### 6.2 Routing Stability 测量

- 测试集上同一 token 多次 forward → 计算 routing 一致性
- DeepSeek-MoE：~95% 的 token 在多次 forward 中选到同一组 top-K
- 说明 router 学到了**稳定的内容相关 routing**，不是随机

### 6.3 反例：Specialization 在某些设置下不明显

- [Mixtral 论文 §5](https://arxiv.org/abs/2401.04088) 报告：8 个 expert 之间**没观察到明显语义专门化**
- 推测原因：N=8 太少，aux loss 强行均衡后 expert 都学"杂烩"
- → Specialization 需要**足够大的 N**（至少 32+）才能浮现

### 6.4 结论

> Specialization 是"效果"，不是"原因"——只有当 N 足够大 + 路由有效时，expert 才会自然分化到特定数据子集上。这也是为什么 DSv3 用 N=256：足够大让 specialization 浮现。

## 七、关键问答

**Q1**：细粒度专家越细越好吗？

- 不是，N 太大有两个上限：
  - **router 算力**：$d \times N$ 线性层开销线性涨
  - **通信开销**：All-to-All 每 token 要发到更多目标
- Krajewski 2024 scaling law：G ≈ 8-16 是 sweet spot，>16 收益边际递减
- 当前 production：N = 128-256，top-K = 6-8

**Q2**：shared expert 数量怎么选？

- DeepSeek-V2：2 个 shared
- DeepSeek-V3：减到 1 个
- 实验过 2-4 个 shared 收益边际递减
- 通用 token 不需要"很多"通用 expert
- 一般 1 个够

**Q3**：dropless 一定要用 MegaBlocks 吗？

- 算法上：dropless = 不丢任何 token
- 实现上：
  - **MegaBlocks**（block-sparse GEMM）：开源主流
  - **Cutlass Grouped GEMM**：NVIDIA 提供的高效变长 batched GEMM，DSv3 用这个
  - **TensorRT-LLM MoE kernel**：NVIDIA 闭源，最快
  - **朴素 padding + mask**：实现简单，但浪费显存
- 三种选一即可

**Q4**：细粒度 + 共享 + dropless 哪个收益最大？

- DeepSeek-MoE ablation 结论：
  - 细粒度（fine-grained）：~3-5% PPL ↓
  - shared expert：~2-3% PPL ↓
  - dropless：~2-5% PPL ↓（capacity 越紧收益越大）
- 三者**正交可叠加**，加起来约 7-12%

**Q5**：Mixtral 8x7B 为什么没采用这些 trick？

- Mixtral 2023-12 发布，时间早于 DeepSeek-MoE (2024-01)
- 走的是 GShard 经典路线（top-2 + aux loss + 8 expert，G=1）
- 实测：Mixtral 在质量上确实弱于同算力 DeepSeek-MoE
- → "用什么 MoE 架构"成为新一轮分水岭

**Q6**：fine-grained 专家更专，能验证吗？

- DeepSeek-MoE 论文做了 heatmap：部分 expert 对中文 / 数学 / 代码强 activation
- shared expert 在所有数据上均匀 active
- Mixtral N=8 时无明显 specialization → N 必须够大
- 工程上 fine-grained 质量数据是确定的

**Q7**：细粒度 expert 训练会不会更慢收敛？

- 不会。专家小 → 每个 expert 更新次数多 → 单 expert 收敛快
- 但总 expert 数多 → 整体训练 token 需求略升
- DeepSeek-V3 vs Mixtral：同 quality 训练 token 数差不多

**Q8**：MoE 层和 dense FFN 层怎么交替？

- 通常 **第一层 dense**（让 attention 输出稳定后再 sparse）
- DSv3：前 3 层 dense FFN，后 58 层 MoE
- Llama-4：奇偶交替 dense / MoE
- 设计原则：早期层学通用特征用 dense 更稳，深层用 MoE 增加容量

**Q9**：shared expert 算总参数吗？

- 算。671B 总参数包括所有 shared + routed expert + attention + embedding
- 但 shared expert 也算 active 参数（每 token 必算）
- 37B 激活 = MLA + embedding + 1 shared + 8 routed + 残差

**Q10**：dropless 在推理时也有效吗？

- 训练时 dropless 是质量必需
- 推理时 dropless 是 latency 优化：减少 padding 开销
- 但推理时 batch 小，dropless 的相对收益降低
- vLLM 推理默认 dropless
