## 一、量化（→ §12.1）

### Q1.1 PTQ vs QAT 区别？主流 LLM 量化方案？ ⭐⭐

**【答 30s】**
- **PTQ** (Post-Training Quantization)：训完再压；用少量 calibration data 算 scale
- **QAT** (Quantization-Aware Training)：训练时就模拟量化噪声
- 主流 LLM 量化基本都是 **PTQ**（训 QAT 成本太高）

| 方法 | 精度 | 特点 |
| --- | --- | --- |
| **GPTQ** (Frantar 2022) | W4 | 基于 Hessian 的逐列量化 |
| **AWQ** (Lin 2023 MLSys) | W4 | 找重要 channel 保留高精度 |
| **SmoothQuant** (Xiao 2022) | W8A8 | activation outlier 转移到 weight |
| **FP8 (E4M3)** | W8A8 | H100 原生支持，DeepSeek-V3 |
| **NVFP4** (Blackwell) | W4A4 | block-fp 格式，2025 新标准 |

**【加分项】**
- GPTQ 数学：minimize `||WX - W_qX||²`，按列贪心
- AWQ 观察：激活的 outlier channel 集中在少数 dim，给这些 dim 留 fp16；其余 INT4
- SmoothQuant：`Y = (X·diag(s)) · (diag(1/s)·W)`，把 activation 难量化的部分挪到 weight

**【追问】**
1. W4A16 和 W8A8 哪个快？→ W4A16 显存省、A16 算力高；W8A8 需要 INT8 tensor core
2. KV cache 量化怎么做？→ per-token 或 per-channel scale，int8/int4
3. 量化掉点多少？→ W4 ~ 1-3 PPL，W8A8 ~ 0.5 PPL，FP8 几乎无损

---

### Q1.2 AWQ 为什么效果好？ ⭐⭐⭐

**【答 30s】**
- 观察：activation 不是各向同性，少数 channel 量级大（"outlier channel"）
- 直觉：这些 channel 对应的 weight 列**对 output 贡献最大**
- 算法：用 activation magnitude 排序，给 top-1% 重要 channel 单独保留 fp16 scale（或留 fp16 整列），其余 INT4
- 不需要反向传播，calibration 几分钟搞定

**【加分项】**
- AWQ 的"activation aware"指利用了 activation 统计指导 weight 量化
- vLLM、TRT-LLM 都集成；HuggingFace Transformers 也支持
- AWQ 在 70B 上掉点 ~0.5（MMLU），是开源 W4 标杆

**【追问】**
1. AWQ vs GPTQ 在 70B 谁更好？→ AWQ 略好，且更稳定
2. AWQ 适合 MoE 吗？→ 适合但每个 expert 单独量化，且 router 不能量化
3. AWQ kernel？→ INT4 GEMM in fp16 outer，需要 dequantize-on-the-fly

## 二、Serving 系统（→ §12.2）

### Q2.1 vLLM 的 PagedAttention 解决什么问题？ ⭐⭐⭐

**【答 30s】**
- **传统 KV cache 问题**：每个请求预分配 max_seq_len 显存，浪费 60-80%（实际 seq 短）+ 碎片化
- **PagedAttention**（Kwon 2023 SOSP）：把 KV 按 **block**（如 16 token）分页，类似 OS 虚拟内存
  - block table 维护虚拟 → 物理映射
  - 显存利用率 > 95%
  - 不同请求间还能 share block（prefix caching）
- vLLM 是 PagedAttention + Continuous Batching 的合一实现

**【加分项】**
- block_size 通常 16 / 32，太小元数据开销大
- Prefix Caching：相同 system prompt 的不同请求共享 KV block（reference count + COW）
- vLLM v0.5+ 引入 chunked prefill + speculative decoding

**【追问】**
1. PagedAttention 怎么实现 attention kernel？→ 收集 block table，每 block 内部连续读
2. block share 怎么保证一致性？→ COW（写时复制），新生成 token 写新 block
3. SGLang 的 RadixAttention 比 PagedAttention 强在哪？→ Radix tree 全自动 prefix share，无需手动 hint

---

### Q2.2 Continuous Batching 怎么工作？ ⭐⭐

**【答 30s】**
- 传统 static batching：等一批请求全完成才进下一批，慢请求拖累快请求
- continuous batching：**每个 decode step 后允许调度**——已完成请求退出、新请求加入，batch 大小动态变化
- 效果：throughput 提升 5-15×

**【加分项】**
- Orca (Yu 2022 OSDI) 是首个 continuous batching paper
- vLLM、TGI、SGLang、TRT-LLM 都用
- 调度策略：FCFS、Priority、Shortest-job-first

**【追问】**
1. continuous batching 和 PagedAttention 是一回事吗？→ 不是；正交但常一起用
2. 不同 seq_len 一起 batch 怎么做？→ padding + attention mask（实际 vLLM 用 PagedAttention 不需要 padding）
3. chunked prefill 怎么和它配合？→ 长 prompt 拆块 prefill，混入 decode batch，避免阻塞短请求

---

### Q2.3 SGLang vs vLLM 区别？ ⭐⭐

**【答 30s】**

| 维度 | vLLM | SGLang |
| --- | --- | --- |
| 主打 | KV management (PagedAttention) | **frontend language + RadixAttention** |
| 调度 | continuous batching | continuous + RadixTree share |
| 复杂 prompt | 弱 | 强（结构化、嵌套、reuse） |
| 生态 | 最广 | 增长快，2024-2025 性能反超 |
| 适合 | 通用 chatbot | agentic、复杂 prompt、多轮 |

**【加分项】**
- RadixAttention：自动检测 prefix 共享、动态合并
- SGLang 还引入 zero-overhead batch scheduler、CUDA Graph、torch.compile 整合
- 2024-2025 在 LLM serving 主流框架排名中 SGLang 上升很快

**【追问】**
1. RadixAttention 数据结构？→ Trie / Radix Tree，节点存 KV block 指针
2. CUDA Graph 怎么帮到 decode？→ 单 step decode 是 fix-shape，graph 捕获后零 kernel launch 开销
3. TRT-LLM 在哪些点强？→ 更激进 kernel fusion + FP8、quantization 集成

---

### Q2.4 LLM serving 一般怎么部署 + 关键指标？ ⭐⭐

**【答 30s】**
- 部署栈：模型加载（vLLM/SGLang）→ load balancer → autoscale → 监控
- 关键指标：
  - **TTFT** (Time To First Token)：首 token 延迟，受 prefill 影响
  - **TPOT** (Time Per Output Token) / **ITL** (Inter-Token Latency)：decode 阶段速度
  - **throughput** (tokens/s, requests/s)
  - **GPU 利用率 / MFU**
- SLO 常见：TTFT < 500ms, TPOT < 30ms

**【加分项】**
- 长 prompt + 短 response：TTFT 关键 → PD 分离 + chunked prefill
- 短 prompt + 长 response（reasoning）：TPOT 关键 → speculative decoding + 量化
- 多租户：prefix caching + 优先级调度

**【追问】**
1. autoscaling 怎么做？→ 看 queue length、GPU util、p99 latency
2. fp16 vs fp8 部署成本对比？→ fp8 单卡能扛 1.5-2× QPS，省显存让 batch 更大
3. Llama-3 70B 在 8×H100 上典型 throughput？→ vLLM ~3000-5000 token/s（batch 32+）

## 三、Speculative Decoding（→ §12.3）

### Q3.1 推测解码的核心思想？ ⭐⭐

**【答 30s】**
- **观察**：decode 阶段 memory bound，GPU 算力闲；可以让小 draft 模型先猜 k 个 token，大 target 一次 verify
- **流程**：
  1. draft 自回归生成 k token
  2. target **并行** verify k+1 个位置的概率
  3. 用 rejection sampling 接受/拒绝
  4. 接受的 token 直接输出，拒绝处 target 自己 sample 一个，丢掉后续
- 期望加速 2-4× 且**数学等价于直接用 target 解码**

**【加分项】**
- 拒绝采样公式：accept 概率 = `min(1, p_target(t) / p_draft(t))`
- 数学等价证明用了 mixture distribution（Leviathan 2022, Chen 2023）
- 接受率高低决定加速比；draft 和 target 越像越快

**【追问】**
1. draft 选什么？→ 同家族小模型（Llama-7B for Llama-70B），或 n-gram，或 EAGLE 蒸馏 head
2. 为什么 target 能并行 verify k token？→ causal mask 让 k 个位置一次 forward 都能算
3. 推测解码改变输出分布吗？→ 不改变，数学等价；这是它的 key selling point

---

### Q3.2 Medusa / EAGLE 1/2/3 / Lookahead 区别？ ⭐⭐⭐

**【答 30s】**

| 方法 | 思路 | 加速 |
| --- | --- | --- |
| **Medusa** (Cai 2024) | target 上加几个 head 直接预测后 k token | ~2× |
| **EAGLE-1** (Li 2024) | 在 last hidden state 上加自回归 head 预测 next-2/3 | ~3× |
| **EAGLE-2** (2024) | 动态 draft tree（重要 branch 展开） | ~3.5× |
| **EAGLE-3** (2025) | training-time test 优化 + multi-level draft | ~4× |
| **Lookahead** (Fu 2024) | n-gram cache + Jacobi iteration，**完全 training-free** | 1.5-2× |

**【加分项】**
- Medusa 简单但接受率不高
- EAGLE-2 是当前开源 SOTA，被 SGLang 集成
- Lookahead 不需要训练 draft，适合不便部署 draft 模型的场景
- 工业上 H100 + Llama-70B + EAGLE-2 可做到 ~120 token/s（batch 1）

**【追问】**
1. EAGLE 怎么训？→ 蒸馏 target 的 hidden state，loss = MSE + CE
2. Tree-based draft（多分支）比 chain 强多少？→ ~30%；EAGLE-2 用动态展开
3. spec decoding 和 batching 冲突吗？→ batch 越大单 step 越长，spec 收益减少；最适合低 batch 高延迟敏感场景

---

### Q3.3 Speculative Decoding 数学等价怎么证？ ⭐⭐⭐

**【答 30s】**
- 设 draft 分布 `q(t)`，target `p(t)`
- 算法：sample `t ~ q`，with prob `min(1, p(t)/q(t))` 接受；reject 则从 `p̃(t) = max(0, p(t)-q(t)) / Z` 重新 sample
- 关键：marginal `Pr(output = t) = q(t)·min(1, p(t)/q(t)) + (1-acc)·p̃(t)`
- 代入展开后等于 `p(t)`，证毕

**【追问】**
1. 这个证明假设 draft 没看 target context？→ 不假设；draft 自回归即可
2. 接受率怎么估？→ E[acc] = Σ min(p(t), q(t))，即两分布的 overlap

## 四、分离式推理（→ §12.4）

### Q4.1 PD 分离（Prefill-Decode Disaggregation）解决什么？ ⭐⭐⭐

**【答 30s】**
- **同机问题**：prefill compute-bound + decode memory-bound 共享 GPU，互相干扰
  - 长 prompt 来了 → prefill 占 GPU → decode 阶段所有请求 TPOT 抖动
- **PD 分离**：prefill 用专门 GPU 池子（大 batch、追求 throughput）；decode 用专门池子（小 batch、追求低延迟）；中间通过 KV 传输衔接
- 代表系统：**Mooncake** (Moonshot)、**DistServe** (PKU)、**Splitwise** (Microsoft)、SGLang 也开始支持

**【加分项】**
- KV 传输是关键瓶颈：用 RDMA / NVLink Switch / GPU Direct Storage
- Mooncake 用 RDMA + KV pool（可跨节点复用）
- 减少干扰：p99 TPOT 抖动可降 5-10×

**【追问】**
1. KV 传输延迟会不会大于收益？→ 70B GQA 4K KV ≈ 1GB，NVLink ~ 5ms 内
2. Prefill 阶段还要不要 chunked？→ 要，长 prompt 仍可能撑爆 prefill 节点
3. 怎么决定 PD 池子比例？→ 看请求分布（avg input/output 长度），动态调

---

### Q4.2 Mooncake / DistServe / Splitwise 区别？ ⭐⭐

**【答 30s】**

| 系统 | 出处 | 重点 |
| --- | --- | --- |
| **Splitwise** (Microsoft 2023) | 首个学术提案 | 静态 PD 切分 + KV migration |
| **DistServe** (PKU 2024) | 学术系统 | Goodput optimization、动态调度 |
| **Mooncake** (Moonshot 2024) | 工业级 | KV pool + RDMA + prefix caching 跨节点 |

**【追问】**
1. KV pool 是什么？→ 跨节点共享的 KV 存储（DRAM/CXL/RDMA），可被 prefill+decode 节点访问
2. 适合所有场景吗？→ 长 prompt / 长 response 场景最受益；短文本 chat 不如同机

## 六、Test-Time Scaling（→ §12.6）

### Q6.1 CoT / Self-Consistency / Best-of-N / Tree Search 区别？ ⭐⭐

**【答 30s】**

| 方法 | 思路 | 成本 |
| --- | --- | --- |
| **CoT** (Wei 2022) | "Let's think step by step" | 1× tokens × 长度因子 |
| **Self-Consistency** (Wang 2022) | sample N 条 CoT，majority vote | N× |
| **Best-of-N (BoN)** | sample N，用 verifier 选最佳 | N× + verifier |
| **Tree of Thoughts (ToT)** | tree search + 中间评估 | N×branch |
| **MCTS** | UCT 搜索 + value model | 高 |
| **rStar** (Microsoft 2024) | 自我博弈 MCTS | 高 |

**【加分项】**
- Self-Consistency 是最简单也最有效的 TTS
- BoN 需要 verifier（process RM / outcome RM）
- ToT 在 24-game / creative writing 强，在 math 不如 MCTS

**【追问】**
1. PRM vs ORM？→ Process Reward 给每步评分（OpenAI Let's Verify）；Outcome 只给最终
2. o1 是 train-time 还是 test-time scaling？→ 两侧都做，但训练里加了 long CoT trajectory
3. R1 怎么 TTS？→ pass@1 vs cons@k，AIME 上 cons@64 给 ~5% bonus

---

### Q6.2 "更长 ≠ 更好"反直觉发现 ⭐⭐

**【答 30s】**
- **Short-m@k**（Hassid 2025）：让模型生成 k 个 short CoT 而非 1 个 long CoT，accuracy 更高 + cost 更低
- **CoT compression**（Yang 2025 等）：训练让 reasoning 更紧凑
- 原因：long CoT 容易越走越偏 + verifier 难选；短 CoT 多样性高 + 投票稳

**【追问】**
1. 什么时候 long CoT 仍然赢？→ AIME 这种难题、需要多步推导
2. test-time compute 应该给 length 还是给 width？→ Snell 2024 "Scaling LLM Test-Time" 发现要根据题目难度动态分

## 七、关键问答（综合）

### Q7.1 一句话说"vLLM 为什么快"？

> PagedAttention 把 KV cache 当虚拟内存管理，零碎片 + prefix share；Continuous Batching 让 decode GPU 不闲；加上 CUDA Graph 和 FlashAttention，吞吐相比 naive 实现 10×+。

### Q7.2 你怎么排 GPU 利用率低的故障？

> 1) 看 prefill vs decode 占比，decode 主导一般 memory bound；2) 看 batch size，太小先 enable continuous batching；3) 看 KV cache 占用，HBM 满了就 OOM 退化；4) 看 kernel timeline（NVProf），找 launch overhead 用 CUDA Graph；5) 看 attention impl，没上 FlashAttention 立刻上。

### Q7.3 Speculative Decoding 在 batch=32 还有收益吗？

> 减弱。batch 大 decode 进入 compute bound 后，spec 的"并行 verify"收益被吃掉。spec 最甜区是 batch ≤ 4，单请求延迟敏感场景（如 chat agent）。

### Q7.4 PD 分离什么场景必须？什么场景反而坑？

> 必须：长 prompt + 强 SLO（如 RAG / code completion）；坑：短 prompt 短 response 场景 KV 传输是净开销。

### Q7.5 FP8 推理 vs INT4 推理怎么选？

> FP8 精度高几乎无损（H100/H200 原生），适合质量敏感；INT4 (AWQ/GPTQ) 显存最省、单卡 70B 可行，适合资源受限。前提：用户能容忍 0.5-1 PPL 掉点。

### Q7.6 EAGLE-2 在 SGLang 上怎么用？

> SGLang 集成 EAGLE 自动启用：target Llama-3-70B + draft（EAGLE head）→ 配置 `speculative_algorithm="EAGLE"` + `num_speculative_tokens=5`。需要 pre-train 的 EAGLE checkpoint（开源有）。

### Q7.7 R1 推理时怎么 budget？

> AIME 难题给 long CoT（max_new_tokens=16K-32K），简单题 short。生产环境用动态 budget：先 sample 几次估算难度，再分配 token 预算。pass@1 vs cons@64 在 AIME 上差 ~5 个点，cons@64 是论文报 SOTA 的常用做法。
