## 一、KV-Cache 与推理经济学（→ §4）

### Q1.1 KV-cache 是什么？为什么需要它？ ⭐

**【答 30s】**
- **现象**：autoregressive 解码每生成一个新 token，都需要重新算 attention，**但 K 和 V 是输入序列的函数，可以缓存**
- KV-cache：把每层每 head 的 K 和 V 存下来，下一步 decode 时只算新 token 的 Q，对 cache 做 attention
- 没有 KV-cache：第 t 步要重算前面 t 个 token 的 K,V，复杂度 O(t²·d) per step，总 O(t³)
- 有 KV-cache：第 t 步只算新 token，复杂度 O(t·d)，总 O(T²·d)

**【加分项】**
- 注意力公式分解：`new_attn_out = softmax([Q·K_cache, Q·k_new]) · [V_cache, v_new]`
- decoder-only 才能用（causal mask 保证 K,V 不随未来变化）
- encoder 没有 KV-cache 概念（一次性 forward）

**【追问】**
1. KV-cache 在 prefill 阶段需不需要？→ prefill 阶段一次性算完所有 K,V 并写入 cache，作为 decode 的起点
2. 为什么不缓存 Q？→ 因为新 token 的 Q 每步都不同，缓存无意义；K,V 来源于已有 token，可复用

### Q1.2 KV-cache 的显存公式？口算一遍 Llama-70B 在 4K context 下占多少？ ⭐⭐

**【答 30s】**

$$
\text{KV cache} = 2 \times n_\text{layer} \times n_\text{kv\_head} \times d_\text{head} \times \text{seq\_len} \times \text{dtype\_bytes}
$$

口算 Llama-70B（GQA 8 KV heads）：
- n_layer = 80, n_kv_head = 8, d_head = 128
- seq_len = 4096, fp16 = 2 bytes
- per token KV = `2 × 80 × 8 × 128 × 2 = 327,680 bytes ≈ 320 KB/token`
- 4K context: `320 KB × 4096 = 1.28 GB`
- batch=8: `~10 GB`

**【加分项】**
- 这是为什么**长上下文 + 大 batch** 把显存吃光
- Llama-2 70B 是 MHA（64 KV heads），同样 4K 是 `64/8 × 1.28 = 10.24 GB`，所以 Llama-3 换 GQA 是降本关键
- DeepSeek-V3 MLA 把 KV 压成 576 dim（不分 head），同等 context 下 **KV 显存只有 GQA 的 ~6%**

**【追问】**
1. KV cache 占 prefill / decode 的瓶颈分别是什么？→ prefill 写 KV、decode 反复读 KV，decode 阶段 KV 是**主要带宽消耗**
2. 量化 KV 到 int8/int4 能省多少？→ int8 直接砍半，int4 砍 4 倍；精度损失 1-3 PPL
3. 1M 上下文怎么办？→ KV 量化 + KV 驱逐 + chunked prefill + 分页（PagedAttention），详 §14.3 / §14.6

### Q1.3 Prefill 和 Decode 的瓶颈分别是什么？（**最经典面试题**）⭐⭐

**【答 30s】**

| 阶段 | 计算量 | 内存访问 | 瓶颈 | 典型 GPU 利用率 |
| --- | --- | --- | --- | --- |
| **Prefill** | O(n²·d) | O(n·d) 读模型权重 | **compute-bound**（GEMM） | 50-80% MFU |
| **Decode** | O(n·d) per step | O(n·d) 读 KV + 读权重 | **memory-bound**（带宽） | 5-15% MFU |

- Prefill：一次性处理 prompt，大矩阵乘法堆满 GPU 算力
- Decode：每步只算 1 token，权重读一遍只算一次乘法，**算力闲死、带宽榨干**
- arithmetic intensity（每 byte 访存做多少次 op）：prefill 高，decode 低

**【加分项】**
- 这就是 vLLM/SGLang 做 **continuous batching** 的根因——单请求 decode 闲，把多请求 decode 凑在一起共享权重读取
- 也是 Mooncake/DistServe 做 **PD 分离**的根因——prefill 用大 batch 高利用率机器，decode 用低延迟机器
- Roofline 模型：op intensity（FLOPs/byte）< 机器 ridge point ⇒ memory bound，反之 compute bound

**【追问】**
1. Decode 能不能 batch 到 compute-bound？→ 可以，batch 大到一定程度算力就饱和，但延迟也涨
2. 为什么 prefill 也要做 chunked？→ 长 prompt 一次性 prefill 会 OOM 或者撑爆 single-token latency
3. spec decoding 改变这个平衡吗？→ 改变；draft 模型让单 step 输出多 token，decode 端伪并行 → 提高利用率

---

### Q1.4 解释 Roofline 模型 + 怎么算 arithmetic intensity？ ⭐⭐⭐

**【答 30s】**
- **Roofline**：x 轴 = arithmetic intensity（FLOPs/byte），y 轴 = throughput（FLOPs/s）
- 两条线：
  - 水平线 = peak FLOPs（compute bound）
  - 斜线 = peak bandwidth × intensity（memory bound）
- ridge point：两线相交，对应"刚好打平"的 intensity
- 你的 kernel 落在斜线段 ⇒ memory bound；落在水平段 ⇒ compute bound

**【加分项】**
- H100 FP16 peak ~989 TFLOPs，HBM3 bandwidth ~3.35 TB/s，ridge point ≈ 295 FLOPs/byte
- attention decode 的 intensity ≈ O(1)（每读一个 KV byte 只做几次乘加）→ 远远 memory bound
- GEMM in prefill 的 intensity ≈ O(d_model)，~几千 → compute bound

**【追问】**
1. MFU 怎么算？→ `实际 throughput / peak FLOPs`
2. HFU 和 MFU 区别？→ HFU 算包括 recomputation 的 FLOPs，MFU 只算有效 FLOPs；HFU ≥ MFU
3. attention 算法上有办法提升 intensity 吗？→ FlashAttention 通过 tiling 把 KV 留在 SRAM，等价提升 intensity

> 训练侧显存四块(参数/梯度/优化器/激活)与 16N 公式的口算题,已迁移到 [§14.4 Q2.2](./04-moe-训练并行题.md)。这里只关注推理侧 KV / 算力指标。

## 二、稠密注意力优化（→ §5）

### Q2.1 FlashAttention 1/2/3 各自核心创新？ ⭐⭐

**【答 30s】**
- **FA1（Dao 2022 NeurIPS）**：**IO-aware tiling** + **online softmax**（增量算归一化），把 attention 从 HBM 搬到 SRAM，等价于把 O(n²) 中间矩阵省掉，提速 2-4×，省 10× 显存
- **FA2（2023）**：优化 warp 调度，让 Q 而非 K/V 走外层循环；提速另外 ~2×
- **FA3（2024，仅 H100）**：用 **TMA**（Tensor Memory Accelerator）+ **WGMMA**（warp-group matmul）+ **FP8** 异步流水线；H100 上接近 75% peak FLOPs

**【加分项】**
- FA 数学上等价于原 attention，**不是近似**
- 关键：增量 softmax 需要维护 running max + running sum，分块算完再合并
- FA3 用 FP8 已经实战上 Llama-3 / Qwen-2.5 长上下文训练

**【追问】**
1. FA 为什么省显存？→ 不显式 materialize n×n attention matrix，只在 SRAM 里 tile
2. FA 在 inference 怎么用？→ vLLM、SGLang、TRT-LLM 都集成
3. FA 处理稀疏 mask？→ FA2 支持 custom mask，但要 mask 是结构化（block sparse）

### Q2.2 MHA → MQA → GQA → MLA 演化为什么？怎么压 KV？ ⭐⭐⭐

**【答 30s】**

| 形式 | KV head 数 | KV cache 倍数 | 代表模型 |
| --- | --- | --- | --- |
| **MHA** | n_q_head | 1× | 经典 Llama-2、GPT-3 |
| **MQA** | **1** | 1/n_q_head | PaLM、Falcon-7B |
| **GQA** | n_q_head / g | 1/g | **Llama-3**、Mistral、Qwen |
| **MLA** | **低秩压缩 + 共享** | ~1/15 | **DeepSeek-V2/V3** |

- **MQA**：所有 Q head 共享一份 K,V；激进省显存但质量略降
- **GQA**：折中——分组共享，Llama-3-70B 用 g=8（64 Q head / 8 KV head）
- **MLA**：把 KV 通过低秩矩阵压缩到一个共享 latent（d=512）后缓存，decode 时再 up-project；KV 显存只有 GQA 的 ~6%；但要解决 RoPE 兼容（decoupled RoPE）

**【加分项】**
- MLA 还要存压缩后的 `c_kv ∈ R^{d_c}`（c_c=512）和一小段 RoPE 维度（d_r=64），合计每 token 576 dim
- MLA 的代价：训练侧多一组 W^DKV / W^UK / W^UV 矩阵，参数量略增
- DeepSeek-V3.2 在 MLA 基础上又加 DSA（Lightning Indexer 选 top-k token），进一步省 KV 读取

**【追问】**
1. MLA 为什么不直接对 K,V 做投影压缩还要解耦 RoPE？→ RoPE 是位置相关的旋转，不能直接和压缩矩阵复合；DeepSeek 把一部分 dim 单独走 RoPE 路径
2. GQA g 怎么选？→ g=8 是经验值，质量 ≈ MHA、KV 砍 8 倍
3. MoBA 和 MLA 是同类东西吗？→ 不是；MLA 压维度、MoBA 路由 block，两者正交

### Q2.3 写一遍 GQA 伪代码？ ⭐⭐

**【答】**

```python
# q: [B, n_q_head, T, d_head]
# k, v: [B, n_kv_head, T, d_head]  with n_kv_head = n_q_head // g

# Step 1: 把 KV 复制 g 次
k = k.repeat_interleave(g, dim=1)   # [B, n_q_head, T, d_head]
v = v.repeat_interleave(g, dim=1)

# Step 2: 标准 attention
attn = (q @ k.transpose(-2,-1)) / sqrt(d_head)
attn = attn.masked_fill(causal_mask, -inf)
attn = softmax(attn, dim=-1)
out = attn @ v   # [B, n_q_head, T, d_head]
```

- **关键**：KV cache 只存 `n_kv_head` 份（省 KV 显存 g 倍）
- inference 时甚至不真做 repeat_interleave，而是在 attention kernel 内部用 broadcasting

**【追问】**
1. FlashAttention 怎么支持 GQA？→ 在 kernel 内部 broadcast KV，不实际复制
2. GQA 训练 from scratch vs 从 MHA 转换？→ 论文 (Ainslie 2023) 提供 mean-pooling KV head 然后 uptrain 几个 step 的方案

### Q2.4 写一遍 RoPE 的实现关键？ ⭐⭐⭐

**【答】**

```python
# x: [B, n_head, T, d]
# 把 d 分成 d/2 对，每对做复数旋转

def rope(x, theta_base=10000):
    B, H, T, D = x.shape
    half = D // 2
    # 每对 dim 的频率
    inv_freq = 1.0 / (theta_base ** (torch.arange(0, half) * 2 / D))
    pos = torch.arange(T).float()
    freqs = pos[:, None] * inv_freq[None, :]   # [T, half]
    cos, sin = freqs.cos(), freqs.sin()
    x1, x2 = x[..., :half], x[..., half:]
    # 复数旋转 (x1 + i x2) * (cos + i sin)
    return torch.cat([x1*cos - x2*sin, x1*sin + x2*cos], dim=-1)
```

**【加分项】**
- 实际实现把 `cos, sin` 预算好放进 buffer
- 长上下文外推：把 `pos` scale（PI）/ 把 `inv_freq` 改造（NTK / YaRN）
- `theta_base` 从 10000 调高到 500K / 1M 是 long-context 标配

**【追问】**
1. RoPE 应用在 Q 还是 K？→ 都应用，且只对相对位置生效
2. base=10000 改成 500000 是什么意思？→ 低频维度旋转更慢，等效拉长有效感受野

## 三、关键问答（综合）

### Q3.1 一句话说"prefill compute-bound, decode memory-bound"为什么对？

> Prefill 算一次大矩阵乘法（batch × prompt × d），arithmetic intensity 高；decode 每步只算一个 token 的 Q 和已有 KV 做 attention，加上权重读取，intensity 低、卡在 HBM 带宽，所以 decode 阶段 GPU 算力利用率（MFU）通常只有 5-15%。

### Q3.2 你怎么决定一个 70B 模型该用 MHA / GQA / MLA？

> 看部署目标：MHA 质量上限但 KV 最重；GQA 是当前性价比最优，Llama-3/Qwen-2.5 都选；MLA 适合**显存敏感 + 长上下文**场景（KV 砍 15×），但训练框架要重写、RoPE 要解耦，工程成本高。除非你做超长上下文 inference，否则 GQA 是默认。

### Q3.3 KV cache 怎么节省？给我列三种方法

1. **维度压缩**：MQA/GQA/MLA（结构改造）
2. **量化**：KV 8-bit（FP8 / int8）、4-bit；vLLM、SGLang 都支持
3. **驱逐**：H2O、SnapKV、Scissorhands —— 只保留高 attention score 的 KV

### Q3.4 FlashAttention 数学上等价吗？它怎么算 softmax？

> 完全等价。online softmax：维护 running max `m` 和 running sum `s`，每来一个 block 算 `m_new = max(m, m_block)`、`s_new = s · e^{m-m_new} + s_block · e^{m_block-m_new}`、output 同步缩放。这样不需要看到完整的 attention matrix 就能算正确的归一化。

### Q3.5 Llama-3 70B 推理一个 4K context、batch=16 大概需要多少显存？

> 权重 fp16 ≈ 140GB；KV cache（GQA 8 head）≈ 320KB/token × 4096 × 16 ≈ 20 GB；激活 ~10GB。合计 ~170GB，需要 2×H100（80GB）以上 + 高效 TP。

### Q3.6 Continuous batching 解决什么问题？

> 静态 batching 中，一个请求 decode 100 步另一个 decode 10 步，10 步那个先结束但 GPU 空 90 步。Continuous batching 在每个 step 后允许新请求加入、旧请求退出，把 decode 阶段 GPU 利用率从 ~10% 拉到 ~50%+。详见 §14.6。

### Q3.7 给我估算 Llama-3-8B 在 H100 上的 decode token/s 上限

> Decode 是 memory bound：每 token 要读完所有权重一遍。8B fp16 = 16 GB，H100 HBM 3.35 TB/s，单 token 上限 ≈ 3.35e12 / 16e9 ≈ **209 token/s**（batch=1）。batch 越大共享权重读取，throughput 几乎线性涨直到 compute bound。这是 §4 经典口算题。
