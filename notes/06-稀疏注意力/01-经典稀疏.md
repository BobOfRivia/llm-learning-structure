## 〇、为什么需要稀疏注意力

### 1. 标准 attention 的"双重爆炸"

标准 self-attention 里，**每个 token 都要和所有 token 计算相关性**：

```
Q @ K^T            →  attention 矩阵 [L, L]    ← 这一步算量随 L² 涨
softmax(...) @ V   →  输出           [L, d]
```

两个量随序列长度 L 同时变大：

1. **算量（FLOPs）**：$QK^T$ 是 $L\times L$ 矩阵，复杂度 $O(L^2 d)$ —— 每层、prefill 阶段全量算一次
2. **KV-cache（显存）**：decode 阶段每个已生成 token 都要把自己的 K、V 留着给后面用，每层 $O(L)$

随着主流上下文从 4k 涨到 128k、1M，两个量都会爆：

| L | Attention 矩阵规模（$\propto L^2$） | KV bytes（FP16, GQA-8, hidden=8k, **单层**） |
|---|----------------------------------|------------------------------------|
| 4k    | 16M（基准）       | 16 MB |
| 32k   | 1G  （×64）       | 128 MB |
| 128k  | 16G（×1024）      | 512 MB |
| 1M    | 1T （×65536）     | 4 GB |

> 第二列是 $L^2$（attention 矩阵元素数），可以理解成"算量基准量"——真实 FLOPs 还要乘 head_dim、head 数、层数。1M token、80 层的模型，**仅 attention 一项就比整个 GPT-3 forward 还多**。
> 第三列只是单层 KV，乘上层数（如 80）后，L=1M 是 **320 GB**——单卡 HBM 装不下。

### 2. 现有优化为什么不够

- **FlashAttention**：把 attention 重写成 tile + online softmax，避免把 $L\times L$ 矩阵写回 HBM。**省 IO，不省 FLOPs**——复杂度仍是 $O(L^2)$。L ≥ 128k 起，算量本身就撑不住。
- **GQA / MQA**：压 K、V 的 head 数，**KV-cache 减小**，但每个 token 仍要 attend 全部 L 个 token，算量没变。

→ 要让长上下文真正可用，必须从根上**减少 token 之间的相关性计算量**，而不只是优化访存或压缩 KV。

### 3. 关键洞察：attention 本来就稀疏

实证观察：训练好的 attention 矩阵里**绝大多数权重接近 0**——每个 query 真正关心的就那么几个 key（局部邻居 + 几个特殊 token + 零星远距离 token）。既然有效信息只在少数位置，那**只算这少数位置**就够了，而且几乎不掉点。

这就是稀疏注意力可行的根本前提：不是"近似 full attention"，而是"**full attention 本身就大部分是浪费**"。

### 4. 稀疏注意力做什么

让每个 token 只 attend 到 $O(k)$ 或 $O(\sqrt{L})$ 个 token，把复杂度从 $O(L^2)$ 降到 $O(L\cdot k)$。问题就归结为一句话：**这 k 个 token 怎么选？**

两条主流路线（对应本章后续几节）：
- **结构化稀疏**（pattern 固定，与输入无关）：sliding window / global / strided / block —— Longformer、BigBird、Mistral
- **数据相关稀疏**（pattern 在 runtime 根据 query 决定）：H2O、Quest、NSA、DSA

本节先讲结构化稀疏，下一节讲数据相关稀疏。

## 一、Sliding Window Attention（局部窗口）

最简单的稀疏：每个 token 只看 **前 w 个 token**。

```
token_i 只 attend token_{i-w}, ..., token_{i-1}, token_i
```

- 复杂度：$O(L \cdot w)$
- 直觉：自然语言中"近距离依赖"占大头
- 缺点：**长距离信息无法传递**（除非靠 stacking layer 的感受野，类似 CNN）

代表用法：
- **Mistral-7B**：window = 4096，配 GQA
- **Longformer**：window + global token（见下节）
- **flash_attn**：`window_size=(left, right)` 参数原生支持

感受野推导：L 层 sliding window 的等效感受野 = $L \cdot w$（叠加扩散）。

---

## 二、Longformer（[Beltagy et al. 2020](https://arxiv.org/abs/2004.05150)）

把 sliding window + **少量全局 token（global attention）** 结合：

```
普通 token i :  只看 window [i-w, i+w]
[CLS] / 关键 token :  attend 所有人 + 所有人 attend 它
```

```
       token 0 [G]   token 1   token 2   ...   token n
G token   ●●●●●●●●●●●●●●●●●●●●●●●●●●●●●●●●●●●●  ← 全局
local         ●●●  ●●●  ●●●   只看附近 w
```

- 复杂度：$O(L w + L g)$，$g \ll L$
- 实证：QA、文档摘要任务，比 sliding-only 强 2-3 分
- 实现细节：global token 需要单独的 Q/K/V projection

---

## 三、BigBird（[Zaheer et al. 2020](https://arxiv.org/abs/2007.14062)）

**三种 pattern 叠加**：

```
1) Window  ：每 token 看附近 w 个      （局部）
2) Global  ：少量全局 token            （概览）
3) Random  ：随机选 r 个 token         （信息混合）
```

- 复杂度：$O(L (w + g + r))$
- 理论保证：能逼近 full attention（universal approximator）
- 实际意义：random 那一路工程上少用，理论价值大于实践

---

## 四、Block-sparse / Strided（GPT-3 sparse、Sparse Transformer）

[Sparse Transformer (Child et al. 2019)](https://arxiv.org/abs/1904.10509) — OpenAI 早期工作。

- **Strided**：每隔 $\sqrt{L}$ 步 attend 一次
- **Fixed**：分块，每个 token attend 自己块 + 一组"summary 块"

```
Block 1 → attend Block 1 + Block 1 的 summary
Block 2 → attend Block 2 + Block 1, Block 2 的 summary
...
```

复杂度：$O(L \sqrt{L})$。

后来主流没普及（理由：block 间信息混合不充分），但 **block-sparse kernel 是 NSA/MoBA 的工程基础**。

---

## 五、Streaming-LLM（[Xiao et al. 2023](https://arxiv.org/abs/2309.17453)）

**关键发现：attention sink**。

观察：标准 transformer 在 decode 长序列时，**最前面几个 token（特别是 BOS）一直被高度 attend**。
原因：softmax 必须把概率分到某处，没有"零分配"的语义出口，模型就把"无用注意力"倒进序列开头。

→ 提出"attention sink" 概念。

```
attention(query_t) = softmax( scores )
                       ↓
              开头的 token 永远拿到一定权重
```

**Streaming-LLM 的方案**（针对长上下文推理）：
- 保留：**前 4-8 个 sink token + 最近 W 个 token**（local window）
- 其余 token 的 KV **直接丢掉**

```
[sink_0 sink_1 sink_2 sink_3]  ......(丢掉中间).......  [window_t-W, ..., window_t]
```

- KV-cache 恒定大小，不再随 L 增长 → **infinite-length decode**
- 模型困惑度稳定（如果只 evict 中间，PPL 立刻爆掉）
- **不能恢复中间信息**（不是真"无限上下文"，是"无限流式生成"）

Streaming-LLM 的工程影响：
- 之后所有 KV 稀疏 / KV eviction 方案都默认保留 sink token
- Cohere、HF transformers 中已经支持 `sink_size` 参数

## 六、H2O — Heavy-Hitter Oracle（[Zhang et al. 2023](https://arxiv.org/abs/2306.14048)）

**关键发现**：长上下文中只有 ~20% 的 token 持续吸引大量 attention，称为 "heavy hitter"。

→ H2O 在 decode 时**动态淘汰非 heavy-hitter 的 KV**：
- 维护一个 "attention score 累加器" 给每个 KV 槽
- 每步：保留 top-k heavy hitter + 最近 N 个 local KV
- 其他 KV 被 evict

```
KV-cache 容量上限 B（如 1024）
  ┌─────────────────────────────────────┐
  │ heavy hitters (top-k累计高分)        │
  ├─────────────────────────────────────┤
  │ recent window（最近 N 个）           │
  └─────────────────────────────────────┘
新 token 来了 → 看是否进 heavy → 顶替旧的
```

- 用 4× 小 KV-cache，在 long context QA 上几乎无掉点
- 是后来 Quest、NSA、DSA 等"数据相关稀疏"的开端

---

## 七、四类方案对比

| 方案 | 稀疏类型 | 复杂度 | KV-cache | 是否数据相关 | 典型用途 |
|------|---------|--------|----------|--------------|---------|
| Sliding Window | 结构化局部 | $O(Lw)$ | $O(w)$ | 否 | Mistral, code |
| Longformer | 局部 + 全局 | $O(Lw + Lg)$ | $O(w+g)$ | 否 | QA, 文档 |
| BigBird | 局部+全局+随机 | $O(L(w+g+r))$ | $O(w+g+r)$ | 否 | 理论 |
| Sparse Transformer | strided/block | $O(L\sqrt{L})$ | $O(\sqrt{L})$ | 否 | 早期生成模型 |
| Streaming-LLM | sink + window | $O(Lw)$ | $O(w + k_{sink})$ | 否 | 流式生成 |
| H2O | heavy-hitter | $O(LB)$ | $O(B)$ | **是** | 长 context decode |

---

## 八、稀疏方案的训练 vs 推理

| 方案 | 训练用 | 推理用 |
|------|-------|--------|
| Sliding Window | ✓（Mistral 训练时用） | ✓ |
| Longformer / BigBird | ✓（早期） | ✓ |
| Streaming-LLM | ✗ | ✓（pure inference trick） |
| H2O | ✗ | ✓（pure inference trick） |

→ 经典稀疏的两条路：**训练时就稀疏**（Longformer/Mistral） vs **训练时全 dense，推理时稀疏**（Streaming-LLM/H2O）。
→ 后者在 2023-2024 是主流（不重训），到 NSA/DSA 时代又回到"训练时就稀疏"。

## 关键问答

**Q1**：sliding window 为什么不会丢长距离信息？
- 单层确实只看 w 个
- 但 L 层叠加后等效感受野 $\approx L \cdot w$（类比 CNN）
- Mistral-7B：32 层 × 4096 = 131k 感受野 → 实际仍能处理长 context
- 但深层信息混合质量不如 full attention

**Q2**：attention sink 为什么存在？
- softmax 的归一化约束：所有权重之和必为 1
- 当 query 跟"附近所有 token"都不太相关时，模型需要"倒掉"注意力
- 训练时序列开头总在视野内 → 模型选它当"垃圾桶"
- 所以 sink 不是 bug，是 softmax 这种归一化机制的副产物

**Q3**：H2O 为什么不需要重训？
- attention pattern 是**模型固有性质**（attention weight 本来就稀疏）
- H2O 只是"利用"这个性质做 KV eviction
- 类比 KV 量化：不动模型，只动 KV 表示

**Q4**：稀疏方案为什么在 dense attention + FA 时代仍有意义？
- FA 把 $O(L^2)$ 的常数压到很低，但**复杂度还是 $O(L^2)$**
- 在 L ≥ 64k 时 FLOPs 仍线性增长不可承受
- 稀疏让复杂度降到 $O(L \log L)$ 甚至 $O(L)$，是 1M+ context 的前置条件

**Q5**：Longformer 和 Mistral 的 sliding window 有什么区别？
- Longformer 配了 global token；Mistral 没有
- Mistral 靠 stacking layer 扩感受野，靠 GQA 省 KV
- Longformer 是早期"显式 long context"，Mistral 是"用窗口做减法 + decoder-only"

**Q6**：稀疏在训练时为什么难？
- 稀疏 mask 经常不规则 → kernel 不好写
- BigBird 的 random pattern 必须打成 block 才能跑（block-sparse kernel）
- 这也是为什么后来 NSA/MoBA 都改成 block-level 选择（FA-friendly）
