# 13.4 长上下文评测（Needle / RULER / LongBench / ∞Bench）

[← 返回框架](../../README.md) · [📎 materials.md → §13.4](../../materials.md)

---

## 〇、本节回答什么

> 厂商敢说"我支持 1M context"，但**真能用**的有多长？这是长上下文 benchmark 要回答的核心问题。本节把"声明的 context 长度"和"实际可用长度"区分开，并梳理 NIAH（玩具）→ RULER（多任务）→ LongBench（真实）→ ∞Bench（极限）的演进。

---

## 一、问题定义：声明 vs 实际可用长度

```
声明长度（claimed）：模型 config / API max_position_embeddings
实际可用长度（effective）：在某 benchmark 上能保持 X% 以上准确率的最大长度
```

例如 GPT-4 Turbo 声明 128K，但在 RULER 上 effective ≈ 64K-100K。差距来自：

- 位置外推不彻底（§12.5）
- attention 稀释 / lost-in-the-middle（成因机制见 [§8.4](../08-长上下文/04-lost-in-the-middle.md)）
- KV 量化 / eviction 带来的损失
- training data 长度分布不足

### 1.1 历史曲线

```
2022  GPT-3.5     4K
2023  GPT-4       8K → 32K → 128K
2023  Claude 2    100K
2024  Gemini 1.5  1M (claimed) → effective ≈ 256K-1M（任务相关）
2024  Llama-3.1   128K
2024  Qwen-2.5    128K (with YaRN)
2025  Gemini 2    2M (claimed)
2025  Llama-4 Scout  10M (claimed!)
```

→ 声明长度膨胀快，实测有效长度跟不上。

## 二、Needle-in-a-Haystack（NIAH） — 最简单的玩具

### 2.1 设计（Greg Kamradt, 2023）

```
1. 取一段超长文本（如 Paul Graham 全部 blog）
2. 在 context 的 depth=d% 位置插入一句"针"：
   "The best thing to do in San Francisco is eat a sandwich and
    sit in Dolores Park on a sunny day."
3. Prompt：
   "What is the best thing to do in San Francisco?"
4. 检查模型是否找到针
```

### 2.2 维度

- **context 长度**：1K → 200K（横轴）
- **针的深度**：0% → 100%（纵轴，0=开头，100=结尾）

输出是一个**热图**，红色表示"找不到"。

```
context →
0%   ████████████████   找到
20%  ██████████░░░░░░   边缘开始失败
50%  ██░░░░░░░░░░░░░░   严重 lost-in-the-middle
80%  ██████████░░░░░░
100% ████████████████   尾部还能找到
```

### 2.3 现状：NIAH 已被打穿

```
GPT-4 Turbo 128K:      100% 全绿
Claude 3.5 Sonnet 200K: 100% 全绿
Gemini 1.5 Pro 1M:      100% 全绿（在 1M）
Llama-3.1 405B 128K:   100% 全绿
```

→ NIAH 现已是**入门体检**，旗舰模型轻松满分。**不能**作为长上下文能力的实质证据。

### 2.4 NIAH 的根本缺陷

- 测的只是 **single retrieval**（找一根针）
- 针和 haystack **完全不同分布**（语义异常显眼）
- 不测 **多跳 / 聚合 / 推理**

→ 模型把"找异常"做成简单 attention spike 就能满分。

## 三、RULER（Hsieh et al., NVIDIA, 2024） — NIAH 升级版

### 3.1 设计动机

NIAH 太弱 → RULER 把 13 个子任务塞进去，覆盖检索 / 多跳 / 聚合 / QA。

### 3.2 13 个子任务

| 子任务 | 类型 |
| --- | --- |
| **single-NIAH** (3 子任务) | 找 1 根针（单 key/单 value/key-value） |
| **multi-key NIAH** | 多个针，要回答某个特定 key |
| **multi-value NIAH** | 同一 key 多 value，要全部找出 |
| **multi-query NIAH** | 多个查询 |
| **Variable Tracking** | x=1, y=x, z=y... 末尾问 z |
| **Common Words Extraction** | 统计高频词 |
| **Frequent Words Extraction** | 与 CWE 类似 |
| **Question Answering**（基于 SQuAD/HotpotQA） | 真实文档 QA |

### 3.3 评测维度

- **长度档**：4K / 8K / 16K / 32K / 65K / 128K
- 每档每子任务报准确率
- 综合 score = 13 个子任务平均

### 3.4 effective context length 定义

> "effective context length = 在该长度上 13 个子任务平均 > X% 的最大长度"
> （X 通常取 85%）

### 3.5 实测（RULER 2024 数据）

| 模型 | claimed | RULER effective@85% |
| --- | --- | --- |
| GPT-4 Turbo | 128K | **64K** |
| Claude 3 Sonnet | 200K | 32K |
| Gemini 1.5 Pro | 1M | **128K** |
| Llama-3.1 70B | 128K | **64K** |
| Mistral Large 2 | 128K | 64K |
| Qwen 2 72B | 128K | 32K |
| Phi-3-mini | 128K | 32K |

→ 声明长度比实测**普遍打 50% 折扣**，这是 2024 长上下文真相。

### 3.6 RULER 为什么权威

- **任务多样**：13 个子任务覆盖多种"长上下文能力"
- **可控生成**：haystack 用 essay 拼接，针用 template 生成
- **可扩展**：把长度档拉到 1M 也容易
- **NVIDIA 出品**：成为业界默认 long context benchmark

## 四、LongBench / LongBench v2（THUDM, 2023/2024）

### 4.1 LongBench v1

- 21 个**真实 NLP 任务**改造为长上下文版
- 平均长度 5K-15K
- 类型：multi-doc QA / summarization / few-shot learning / code completion

### 4.2 LongBench v2 (2024-11)

- 升级到 **8K-2M token**
- 503 道高难度多选题
- 经过人工 verify（去除模糊答案）
- 模型测试需要 **CoT**，纯抽取不解决

### 4.3 与 RULER 的区别

| 维度 | RULER | LongBench |
| --- | --- | --- |
| 数据来源 | 合成（针 + essay haystack） | 真实文档 |
| 任务类型 | 13 个合成模板 | 21 个真实 NLP 任务 |
| 评测重点 | retrieval / 跟踪 | comprehension + reasoning |
| 易解释性 | 强（每子任务清晰） | 较弱 |

→ **RULER 测"找得到"，LongBench 测"用得起来"**，两者互补。

## 五、∞Bench / NoCha / BABILong（极限长度）

### 5.1 ∞Bench（Zhang et al., 2024-02）

- **平均 200K token**，最长 2M
- 任务：长书 QA / Math / Code retrieval
- 含数学和代码的长上下文版

### 5.2 NoCha (Novel Challenge, 2024)

- 用**未发布的小说**做"针 + 多跳推理"
- 测试**真实长文档理解**
- 抗污染（小说是私有的）

### 5.3 BABILong (Kuratov et al., 2024)

- 把经典 bAbI 推理任务（chain of reasoning）的针塞进 haystack
- 长度档：0K → 50M（用 ICL 喂多次）
- 测**长上下文 + 推理链**

### 5.4 LV-Eval / LooGLE

- 中文长上下文 benchmark
- 长文档 QA

## 六、其他重要 benchmark

### 6.1 Helmet（Yen et al., 2024）

- 综合长上下文 benchmark
- 覆盖 7 个任务类型，长度 32K-128K
- **报数风格类似 RULER**

### 6.2 LongQA / Loong / Marathon

- 各种长上下文 QA benchmark
- 区分度有限

### 6.3 NIAH 变种

- **Multi-needle NIAH**：插多根针
- **Adversarial NIAH**：针和 haystack 语义相近（更难定位）
- **Distractor NIAH**：插混淆针
- **Multi-turn NIAH**：跨对话回合

### 6.4 LOFT (Long-context Frontiers, Google, 2024)

- Google 推出，覆盖 RAG / SQL / Code
- 长度 32K-1M
- 用于评 Gemini 1.5 vs RAG-only 系统的对比

## 七、评测工程坑

### 7.1 token 化口径不一致

不同 tokenizer，同一文本 token 数差 20-30%。报"128K context"时必须注明 tokenizer。

### 7.2 Prompt 风格影响

NIAH / RULER 的针位置对 prompt 中的"system / user / assistant"层级敏感。chat 模型套 chat template 后表现可能差异巨大。

### 7.3 KV 量化影响

很多模型默认开 FP8 KV / KIVI 评测。RULER 在 65K 以上**会因 KV 量化掉 5-15 点**。报 long context 数字时**必须注明 KV precision**。

### 7.4 max_new_tokens

reasoning 模型评 long context 时，输出可能也很长，**输出空间不够**会掉点。

### 7.5 算力

RULER @128K × 13 子任务 × 50 样本 ≈ **几百万 prefill tokens**。一次完整评测可能 100+ GPU-hour（A100）。

## 八、与 §8 / §12.5 的联动

```
§8     长上下文训练（YaRN/Position interpolation 训练侧）
§12.5  长上下文推理（KV 量化/eviction/chunked prefill 推理侧）
§13.4  评测侧 — 验证 effective context
```

举例：

- Llama-3.1 训练用 YaRN scaling factor 8（§8.4 / §12.5）→ §13.4 用 RULER 验证 effective ≈ 64K（而非声称的 128K）
- StreamingLLM / H2O / SnapKV 这类**推理时压 KV** 的方案 → 评测惯例是在 RULER / LongBench 上对比"不压 vs 压"的损失

## 九、关键问答

**Q1：NIAH 满分能不能说明模型 long context 强？**
A：**不能**。NIAH 只测最简单的 single retrieval，2024 起所有旗舰模型都满分。需要看 RULER / LongBench / ∞Bench 才能判断真实能力。

**Q2：effective context length 怎么算？**
A：在 RULER 这种多任务 benchmark 上，定义"13 子任务平均准确率 ≥ 85%"的最大长度。比 claimed length 通常打 50% 折扣。

**Q3：为什么模型在 NIAH 上满分却在 RULER 上掉？**
A：NIAH 只测"找异常"。RULER 加入了：
- **Variable Tracking**（多步状态追踪）
- **多 needle 聚合**（不是找一个，是找一组）
- **Common Words Extraction**（统计性任务）
这些 attention 不能简单 spike 解决。

**Q4：LongBench 和 RULER 选哪个？**
A：**都报**。RULER 测"机械能力"（retrieval/tracking），LongBench 测"实用能力"（real QA/summary）。一个模型在两者都好才算真长上下文。

**Q5：为什么不能用 BookCorpus 这类原始长文档评测？**
A：(1) **任务定义模糊**（多长才算"理解"了一本书）(2) **难评分**（开放式生成）(3) **污染**（很多书在训练数据里）。所以 long context benchmark 都用合成针 / 私有文档 / 多选题来规避。

**Q6：1M context 模型怎么测？**
A：(1) RULER 拉到 1M 档（NVIDIA 已公布数据）(2) BABILong（推理链 + 长度）(3) LOFT（Google 推出）(4) ∞Bench 极限 2M。算力代价巨大——单条 prefill ≈ 1M 个 token ≈ 数十 GPU-second。

**Q7：长上下文评测和 RAG 评测怎么区分？**
A：long context = "**全塞进 context**" vs RAG = "**先检索再塞**"。LOFT 是 Google 设计的对照 benchmark，测"全塞 1M Gemini" vs "RAG-only" 的差距。结论：**全塞胜率高但贵**，RAG 经济但易丢长程依赖。生产中常**组合**：粗筛用 RAG 召 100K，再全塞模型。
