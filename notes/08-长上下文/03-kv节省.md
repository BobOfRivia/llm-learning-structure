# 8.3 KV 节省（H2O / SnapKV / StreamingLLM / PyramidKV — 算法层）

## 〇、这一节回答什么

§8.1 是训练侧，§8.2 是位置编码。本节是**推理侧的"算法层"**:

> 模型已经训好了（支持 128k 或 1M），但推理时 KV-cache 还是太大。
> **哪些 KV 可以安全地丢掉而不掉点？** —— 这是算法问题。

KV-cache 大小：
$$\text{KV size} = 2 \cdot L \cdot n_{layers} \cdot n_{heads} \cdot d_{head} \cdot \text{precision}$$

对 Llama-3-70B + L=128k + FP16：约 **42 GB**（单 batch）。→ 必须节省。

---

## 一、KV 节省的三大方向

```
1. Drop / Evict       ── 把"不重要"的 KV 永久丢掉      ← H2O / SnapKV / Streaming-LLM / PyramidKV  (本节)
2. Compress            ── 把 KV 压缩到低秩 / 低精度       ← MLA(§5.4) / KV 量化(§12.5) / KIVI(§12.5)
3. Manage / Schedule   ── 分块管理 + 分页 + chunked prefill  ← PagedAttention(§12.2) / Chunked Prefill(§12.5)
```

本节聚焦 **1（drop 算法）**。压缩与调度的工程展开在 §12 推理优化章。

## 二、H2O — Heavy Hitter Oracle

[Zhang et al. 2023 — H2O](https://arxiv.org/abs/2306.14048)。

### 2.1 观察

实测：少部分 token（"Heavy Hitter"，H2）累积 attention 分数远高于其他 → drop 掉非 H2 token 的 KV，质量几乎不掉。

```
对每个 head：
  累积 attention score: a_i = Σ_t α_{t,i}    （i 是历史位置）
  H2 token = a_i 排名 top 部分
```

### 2.2 算法

```
KV-cache 满了 (size > budget) 时:
  for each new token:
    保留所有 H2（top-k 累积分数）
    其余按 recent 策略保留最近 m 个
    其他 KV: evict
```

→ KV-cache 维持在固定 budget B，长 context 推理 → 推理显存恒定。

### 2.3 经验

- B ≈ L/4 ~ L/8 时，质量几乎不掉
- 极致压缩（B ≈ L/16）开始明显掉点
- **不需要重训**，属于纯推理侧 trick

## 三、StreamingLLM — Attention Sink

[Xiao et al. 2023 — StreamingLLM](https://arxiv.org/abs/2309.17453)。

### 3.1 观察

实测：模型的 attention 在 **最前面几个 token**（如 BOS 或前 4 个）始终有显著分数 → 这些是 **"attention sink"**。

→ 即使内容无意义，把它们 drop 掉会直接崩。

### 3.2 算法

保留两部分：
1. **Attention sinks**：最早的 4 个 token（不动）
2. **Sliding window**：最近的 W 个 token（如 W=2048）

中间的 token 全部 evict。

```
KV layout:
[ sink_0 | sink_1 | sink_2 | sink_3 | ... drop ... | recent W tokens ]
```

→ 可以**无限长流式生成**而 KV-cache 大小恒定 = 4 + W

### 3.3 适用

- 流式对话 / 流式 ASR / 长对话窗口
- 不适合 long-context retrieval（中间的"针"被丢了就找不到）

→ StreamingLLM 解决"**任意长流式**"，不解决"**任意长 retrieval**"。

## 四、SnapKV — Prompt-aware 一次性压缩

[Li et al. 2024 — SnapKV](https://arxiv.org/abs/2404.14469)。

### 4.1 观察

H2O / StreamingLLM 在 **decode 阶段**动态 drop。但实际场景：
- prefill 阶段，prompt 已经全部喂入
- 此时可以**一次性看完整 prompt 的 attention**，决定哪些 KV 留下

### 4.2 算法

```
prefill 完成后：
  for each head, 用 prompt 末尾的最近 N 个 token 的 attention 投票
  选 top-k token 的 KV 保留，其他直接丢
  之后 decode 只读这一份精简 KV-cache
```

→ 类似"先全看完，再压缩"，比逐步 drop 更准。
→ 长 prompt + 短 generation 场景非常划算（如 RAG、long-doc QA）。

### 4.3 与 H2O 对比

| 维度 | H2O | SnapKV |
|------|-----|--------|
| 时机 | decode 时滚动 evict | prefill 完成后一次压缩 |
| 压缩比 | 4-8× | 4-16× |
| 长 prompt + 短 gen | 好 | 更好 |
| 长 gen 流式 | 好 | 不适合（无更新） |

## 六、KV 压缩 vs KV 节省的全景图

```
                  ┌──────────────────────────────┐
                  │       架构层 (训练时)        │
                  │  MLA / GQA / Sliding window  │
                  └──────────────┬───────────────┘
                                 │
                  ┌──────────────▼───────────────┐
                  │   推理优化层（不重训）       │
                  ├──────────────────────────────┤
                  │ Drop:  H2O / SnapKV / Stream │
                  │ Quant: INT8 / FP8 / KIVI     │
                  │ Manage: Paged / Chunked      │
                  └──────────────────────────────┘
```

- **训练侧**：MLA / GQA 是从架构上省 KV（见 §5.3、§5.4）
- **推理侧**：本节方法是部署时再省一层
- **可叠加**：MLA + INT8 KV + chunked prefill + SnapKV 同时启用

---

## 八、何时选哪一个

| 场景 | 推荐 |
|------|------|
| 普通 4-32k 推理 | GQA + INT8 KV + PagedAttention（够用） |
| 长 prompt + 短 gen（RAG、long-doc QA） | **SnapKV** + INT8 KV |
| 长流式生成（小说续写、长对话） | **StreamingLLM** + sliding window |
| 长 prompt（128k+）但 KV 够放 | chunked prefill 必开（峰值显存） |
| 极致省 KV，不愿重训 | H2O + INT4 KV + PagedAttention |
| 重训允许 | 直接 MLA（一个数量级） |

## 九、关键问答

**Q1**：H2O / SnapKV 会不会丢长 context retrieval（"针在草堆"任务）？
- 会，且通常 NIAH 评测能验证
- H2O：B ≈ L/8 时 NIAH 仍可（H2 倾向于覆盖重要 token）
- SnapKV：长 prompt 一次性看完，召回更好
- 但都不如 dense 完整 KV

**Q2**：Streaming-LLM 的 attention sink 为什么是前几个 token，不是其他？
- LLM 自回归训练中，前几个 token 是所有后续 token 的 attention 来源
- softmax 要求 attention 必须有出口 → 自然倾向"前几个"作为 sink
- 任何位置都行，但前几个最稳定（BOS / 高频起始 token）

**Q3**：SnapKV 在 chat 多轮场景中怎么办？
- 每轮 prompt 都 prefill 一次 → SnapKV 每轮可以重新压缩
- 但跨轮的"压缩后 KV"不能复用（因为 prompt 内容变了）
- 多轮场景建议：H2O 或保留完整 KV + INT8 量化

**Q4**：Chunked prefill 会不会让 attention 不准？
- 不会，attention 数学上完全等价
- 区别只是"何时算"，不是"算什么"
- 唯一开销：每 chunk 有一些重复读取（缓存命中可缓解）

**Q5**：H2O 和 sliding window 的关系？
- sliding window：**位置无关**地丢早期 token
- H2O：**内容相关**地选 heavy hitter
- H2O 在大多数任务上质量更好（保留了"重要的早期 token"）
- 但工程上 sliding window 实现更简单（无需 attention score 统计）

**Q6**：KV 节省的极限在哪？
- 实验：极致压到 L/64 时仍能保留部分能力，但 NIAH 等任务明显崩
- 一般建议：B ≥ L/8 + INT8 量化是"安全档"
- 进一步压必须重训（MLA / Mamba 路线）

**Q7**：为什么 vLLM 默认开 PagedAttention 而不是 H2O？
- PagedAttention：**显存分配优化**（无质量损失，纯工程）
- H2O：**质量 trade-off**（用质量换 KV 大小）
- 默认开无损方案，损失类方案用户自选
